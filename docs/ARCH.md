## 1. 一页看懂

**做什么。** 一个 AFDX 端系统。它有两个方向的工作：

- 发送：应用交来一段数据，并指明走哪条虚拟链路（VL）。端系统按这条 VL 的最小发送间隔（BAG）把数据装成以太网帧，同时从 A、B 两个网口发出去。
- 接收：两个网口收到帧后，检查帧是否完好、序号是否连续；A、B 两份只留先到的一份，再把数据交给应用。

**如何支持 128 条发送 VL 和 4096 条接收 VL。** 配置和逐 VL 状态放在块 RAM 中，用顺序访问控制规模；连续字节通路用预读流水维持带宽：

1. 每条 VL 的配置和状态都放进块 RAM，下文叫“表”。
2. 每张表只由一个状态机按顺序读写，一个周期只做一小步。
3. 收发数据通路每周期处理一个字节，最短帧连前导和帧间隔占 84 个周期。128 条发送 VL 顺序扫描约需 300 个周期，因此保留提前 512 周期选候选、预备下一帧的调度；不能再用“扫描短于最短帧”解释小帧线速。

**三个总体选择。**

| 选择 | 内容 | 依据 |
|---|---|---|
| 单时钟 | 全设计只有一个 125 MHz 时钟，没有跨时钟域 | 官方答疑 1008 版 R59、R61：时钟与 GMII 接口速率匹配；用户确认 |
| 官方 8 个端口走真实数据 | `tx_data/tx_valid` 和 `rx_data/rx_valid` 是 A 网的 GMII 字节流，每拍一字节，含前导和 FCS | 官方答疑：给 MAC 层的接口是 GMII；可以酌情增加新接口 |
| 自己写 MAC | 前导、帧起始符、CRC32、帧间隔由本设计的小模块完成 | 官方答疑：可以调用 eLinx 的 IP（不是必须）；答疑 R57 允许用厂商生成的 .vo 仿真；本方案沿用已经验证的自有 MAC |

**线速率和吞吐率。** GMII 与收发核心均每拍一个字节，帧内速率 1 Gbit/s。1471 字节载荷的满帧加前导、FCS 和 12 拍帧间隔共 1538 拍，理论载荷率约 956.44 Mbit/s；实际速率仍按发送字节及接收交付裁窗测量，冗余份不叠加。T16 的 77/81 条 VL 双向实测分别为 906.136/953.208 Mbps，BAG 都是 125000 拍。

**官方依据与方向。** 官方答疑 1008 版 R58 要求吞吐达到 100 Mbps，R59 要求时钟匹配接口，R60 要求 GMII 时延不超过 2 ms，R61 确认八位口是 GMII、MAC IP 可选，R62 不检查 ready、valid 表示当拍字节有效，R46 允许综合后仿真。T16 按用户批准改为原生千兆通路，保留原 32 项 RTL 回归的功能与异常，另测集中释放突发；完整网表回归及五功能网表留 T17。

## 2. 顶层端口

模块名固定为 `AFDX_top`。官方 8 个端口的名字、方向、位宽不变。

| 端口 | 方向 | 含义 |
|---|---|---|
| `clk` | 入 | 125 MHz，8 ns |
| `reset` | 入 | 同步复位，高有效（暂定，官方没说明极性） |
| `tx_data[7:0]`、`tx_valid` | 出 | A 网发送：字节和“帧正在发送”指示，相当于 GMII 的 TXD、TX_EN |
| `rx_data[7:0]`、`rx_valid` | 入 | A 网接收：相当于 GMII 的 RXD、RX_DV |
| `tx_ready` | 出 | 复位后各表清零完成、端系统可以工作时为 1 |
| `rx_ready` | 入 | 不使用（官方答疑：ready 信号可以不用到） |
| `tx_data_b[7:0]`、`tx_valid_b`、`rx_data_b[7:0]`、`rx_valid_b` | 出/入 | B 网，含义同 A 网 |
| `app_tx_valid`、`app_tx_ready`、`app_tx_data[7:0]`、`app_tx_last`、`app_tx_vl[6:0]` | 入/出 | 应用发送：一条消息是一串字节，`last` 标最后一个字节，`vl` 在第一个字节时取样；`app_tx_ready` 直接接 `m_ready` |
| `app_tx_port_en`、`app_tx_sport[15:0]`、`app_tx_dport[15:0]` | 入 | 接消息接口的 `m_port_en`、`m_sport`、`m_dport`，和 `app_tx_vl` 一样在第一个字节取样。这样一条 VL 可以带多个 UDP 端口 |
| `app_rx_valid`、`app_rx_data[7:0]`、`app_rx_last`、`app_rx_vl[11:0]`、`app_rx_port[15:0]` | 出 | 应用接收：每周期一个字节，不带反压；`app_rx_port` 接 `d_dport`，`app_rx_vl` 接 `d_vl` |
| `app_rx_sport[15:0]`、`app_rx_net` | 出 | 接 `d_sport`、`d_net` |
| `ev_tx[6:0]` | 出 | 发送核心的七个统计脉冲，位 0 到位 6 依次是 accept、drop_dis、drop_full、drop_long、drop_nopage、tx_a、tx_b |
| `ev_a[7:0]`、`ev_b[7:0]`、`ev_rm_drop`、`ev_deliver` | 出 | 接收核心的统计脉冲 |
| `ev_gdrop[1:0]` | 出 | 保留的 A/B 接收适配溢出脉冲端口，当前无适配器，固定为 0 |
| `cfg_wr`、`cfg_rd`、`cfg_addr[17:0]`、`cfg_wdata[31:0]`、`cfg_rdata[31:0]`、`cfg_rvalid`、`cfg_ready` | 入/出 | 配置和统计总线，见第 7 节 |

参数 `TX_PAGE_AW`、`TX_OFF_AW`、`LOOKAHEAD`、`RX_RING_AW`、`RX_DQ_AW` 的默认值为 8、9、512、12、5，原样传给核心。`tx_ready` 仍是两个核心的 `init_done` 相与后打一拍。`rx_ready` 不使用，`app_tx_ready` 直接接 `m_ready`。顶层 40 个端口声明共 259 位，低于所用器件 339 个 I/O。A/B GMII 直接连接两个核心。

**端口上的字节节拍。** 外部 GMII 每周期一个字节，`valid` 为 1 就表示当前字节有效，不与 ready 握手。

- 发送：`tx_valid` 从第一个前导字节到 FCS 最后一个字节连续为 1；核心输出就是 GMII 输出，适配延迟为 0，帧间空闲至少 12 周期。
- 接收：`rx_valid` 上升开始一帧，下降结束；MAC 将输入先寄存，再逐拍剥离前导和 FCS。无需缓存整帧后重放，单个低周期也可隔开输入两帧；帧内容、环形缓冲和描述队列仍分别执行第 6 节的检查与回退。
- 复位期间输出为零；接收清表完成前开始的帧整帧忽略，清表完成不会把半帧认成新帧。单时钟接口以共同 `clk` 采样，不增加 PHY、接收时钟或跨时钟域。

## 3. 帧格式

n 是应用数据的字节数，1 ≤ n ≤ 1471。

| 字节位置 | 长度 | 内容 |
|---|---|---|
| 0–3 | 4 | `03 00 00 00`（P7 规定的目的 MAC 固定部分） |
| 4–5 | 2 | VLID，高字节在前 |
| 6–8 | 3 | `02 00 00`（P7 规定的源 MAC 固定部分） |
| 9–10 | 2 | 端系统用户 ID（寄存器） |
| 11 | 1 | 接口号：A 网 `0x20`，B 网 `0x40` |
| 12–13 | 2 | `08 00`（IPv4） |
| 14–33 | 20 | IPv4 头：`45 00`，总长度 n+28，标识（每发一帧加 1），`00 00`，TTL `01`，协议 `11`，头校验和，源 IP，目的 IP |
| 34–41 | 8 | UDP 头：源端口，目的端口，长度 n+8，校验和（v0.1 填 0） |
| 42 起 | n | 应用数据 |
| 其后 | 17−n | n 小于 17 时补 0 到 17 字节 |
| 再后 | 1 | 序列号 SN |
| 最后 | 4 | FCS（CRC32，MAC 自动加） |

- 含 FCS 的帧长 = 47 + max(n, 17)，范围 64 到 1518。
- A、B 两份帧只有第 11 字节和 FCS 不同。
- SN：复位后每条 VL 的第一帧为 0，之后 1、2、…、255、1、2、…（255 的下一个是 1）。
- 组播目的IP按664P7图3-38配置为 `224.224.VLID[15:8].VLID[7:0]`，即 `0xE0E00000 | VLID`；发送核心直接使用配置表中的目的IP。系统测试的用户及组播服务VL使用此格式，615A服务VL使用对端单播IP。

## 4. 时间基准

| 名称 | 含义 |
|---|---|
| `now[31:0]` | 自由运行的周期计数器，复位时为 0，之后每周期加 1，约 34.36 秒回绕。比较早晚一律用“相减看符号位” |
| `byte_en` | 正常工作固定为 1，A/B 发送每周期都可处理一个字节；模块级突发测试可暂置 0 预装队列 |
| `now_c[15:0]` | 粗计时，等于 `now[27:12]`：每 4096 个周期（32.768 µs）加 1，约 2.147 秒回绕，只给接收侧的冗余管理用 |

这三个信号由模块 `afdx_timebase` 产生，端口：`clk`、`reset`、`now`、`byte_en`、`now_c`。

每个时钟周期都是发送字节边界，起点与 BAG 不再量化到 8 的倍数。`now` 和 `now_c` 的计数及回绕定义保持不变；BAG=100003 的模块回归实测间隔也恰为 100003 拍。

## 5. 发送侧

```
应用 / 服务 ──► tx_buf ──► 载荷 RAM（分页）
                  │ 登记                │ 读
                  ▼                     ▼
              tx_engine ──授权──► tx_builder ──► mac_tx ──► A 网
            （VL 状态表）                              └──► B 网
```

### 5.1 表

都用 `afdx_ram_sdp`（一个写口、一个读口、同步读）。每张表的写口和读口各只归一个模块。

| 表 | 深度×位宽 | 写口归谁 | 读口归谁 | 内容 |
|---|---|---|---|---|
| `tx_cfg` | 1024×32 | 配置总线（清表期间归初始化状态机） | tx_engine | 每条 VL 占 8 个字，地址 = {VL 序号[6:0], 字序号[2:0]}，内容见下表 |
| `tx_state` | 128×63 | tx_engine | tx_engine | `timer_active`、`next_time`[31:0]、`sn`[7:0]（下一帧要用的序号）、`q_count`[5:0]、`q_head`[7:0]、`q_tail`[7:0] |
| `tx_mnext` | 256×8 | tx_engine | tx_engine | 同一条 VL 队列里的下一条消息（用消息的首页号表示） |
| `tx_desc` | 256×44 | tx_buf | tx_engine | 消息描述：`len`[10:0]、`port_en`、`sport`[15:0]、`dport`[15:0]，按首页号存放 |
| `tx_pnext` | 256×8 | tx_buf | tx_builder | 一条消息内的下一页 |
| `tx_payload` | 131072×8 | tx_buf | tx_builder | 128 KiB 应用数据，地址 = {页号[7:0], 页内偏移[8:0]} |
| `tx_free` | 256×8 | `afdx_tx_free` | `afdx_tx_free` | 空闲页号的 FIFO，见下 |

**空闲页 FIFO `afdx_tx_free`。** 一块 RAM 加读写指针和计数。复位后它自己把页号 0 到 `TX_PAGES−1` 依次装进去，装完之前不出页。三个口，都带握手：

- 取页口：tx_buf 用。
- 还页口 1：tx_builder 用，读完一页还一页。两个还页口同时有请求时它优先。
- 还页口 2：tx_buf 用，放弃一条消息时把已用的页还回来。

`tx_cfg` 每条 VL 的 8 个字：

| 字 | 内容 |
|---|---|
| 0 | `en`[0]、`net_a`[1]、`net_b`[2]、`qmax`[8:3]（本 VL 最多排队几条消息）、`max_payload`[19:9]（本 VL 允许的最大 n） |
| 1 | `bag`：最小发送间隔，单位是时钟周期（1 ms = 125000）。不超过 2^30（约 8.59 秒）：早晚是按 32 位相减看符号位判的，再大就会判反 |
| 2 | `vlid`[15:0] |
| 3、4 | 源 IP、目的 IP |
| 5 | 默认源端口[31:16]、默认目的端口[15:0] |
| 6、7 | 保留 |

`net_a` 和 `net_b` 都为 0 的 VL 按未启用处理。六个字合成一张表是为了省块 RAM（见第 11 节）；tx_engine 一拍读一个字，授权一帧时依次读完，时间绰绰有余。一条 VL 有消息在排队或正在发送时改它的配置，结果不保证；配置应在使用这条 VL 之前写好。

参数：`TX_VL_COUNT = 128`（固定），`TX_PAGE_AW = 8`（256 页），`TX_OFF_AW = 9`（每页 512 字节）。最长消息占 3 页，不超过 512 字节的消息占 1 页；77/81 条最长消息同时驻留分别占 231/243 页。每页 256 字节的原参数及 `TX_PAGE_AW=5`、`TX_OFF_AW=11`（32 页、每页 2048 字节）仍由模块回归覆盖，页号表位宽不变。

### 5.2 tx_buf：收下应用消息

消息接口（应用和各服务共用同一种）：`m_valid`、`m_ready`、`m_data[7:0]`、`m_last`、`m_vl[6:0]`、`m_port_en`、`m_sport[15:0]`、`m_dport[15:0]`。`m_vl` 和三个端口信号在消息的第一个字节取样。`m_port_en` 为 0 时用 `tx_cfg` 字 5 的默认端口。

1. **开始。** 第一个字节到来时从 `afdx_tx_free` 取一页。没有空闲页：整条丢弃，记“无空闲页”。
2. **接收。** 边收边写 `tx_payload`；写满一页就再取一页，并在 `tx_pnext` 里登记。本条消息用过的页号另存在最多 6 个寄存器里。取页的几拍里 `m_ready` 为 0，其余时间每拍收一个字节。
3. **放弃。** 字节数超过 1471，或中途取不到页：停止写入，把已用的页从还页口 2 还回去，本条消息剩下的字节收下丢掉，分别记“超长”“无空闲页”。
4. **入队。** 最后一个字节写完后写 `tx_desc`，向 tx_engine 发入队请求（VL 序号、首页号、长度）。tx_engine 回答“收下”或“不收”和原因，时限见第 5.3 节；等回答期间 `m_ready` 为 0。不收：把已用的页还回去，按原因计数。
5. 丢弃一条消息不影响后面的消息，也不能漏还任何一页。被丢弃的消息占过的页，在给出它的统计脉冲之前全部还回，所以下一条消息能不能取到页，不受上一条被丢弃的消息影响。

统计用的单周期脉冲：`ev_accept`（收下）、`ev_drop_dis`（VL 未启用）、`ev_drop_full`（队列满）、`ev_drop_long`（超长）、`ev_drop_nopage`（无空闲页）。每条消息恰好给其中一个，时间在它的最后一个字节被收下之后 96 个周期以内、下一条消息的最后一个字节被收下之前。所以按先后顺序，第 k 个脉冲对应第 k 条消息。

`m_ready` 连续为 0 不超过 96 个周期（清表完成之后）。空闲页用完时消息被丢弃，不是让应用等。

### 5.3 tx_engine：`tx_state` 的唯一主人

它是一个状态机，一次只做下面一种操作。两个请求同时到，按表里从上到下的顺序先后做。表里的时限从这个操作开始做算起；算上排在前面的操作，入队请求从发出到得到回答不超过 64 个周期。

| 操作 | 触发 | 做什么 | 时限 |
|---|---|---|---|
| 起始确认 | tx_builder 报告帧开始发送的时刻 `t_start` | 写 `next_time = t_start + bag`，`timer_active = 1`；清 `pend_vl` | 16 个周期内做完 |
| 入队 | tx_buf 的入队请求 | 读 `tx_cfg` 字 0 和 `tx_state`。按顺序检查：`en` 为 0 或两网都没启用，答“未启用”；长度大于 `max_payload`，答“超长”；`q_count` 不小于 `qmax`，答“队列满”。都通过就入队：队列为空则 `q_head = q_tail = 首页号`，否则写 `tx_mnext[q_tail]` 并更新 `q_tail`；`q_count` 加 1。入队后如果当前没有候选、这条 VL 不是 `pend_vl`、并且 `soon` 成立（见下），直接把它定为候选 | 16 个周期内回答 |
| 授权 | 有候选，且 tx_builder 的“下一帧”位置空着 | 依次读 `tx_cfg` 的字 0 到字 5、`tx_desc[q_head]`、`tx_mnext[q_head]`，把这一帧的全部字段交给 tx_builder；出队（`q_head` 前移、`q_count` 减 1），`sn` 换成下一个值；`bag` 留在寄存器里给起始确认用；这条 VL 记进 `pend_vl` | 24 个周期内交出 |
| 扫描 | 没有候选时 | 按 `scan_ptr` 逐条看 VL，见下 | 每 2 个周期看一条 |

**`pend_vl`。** 一帧从授权到真正开始发送之间，这条 VL 的 `next_time` 还是旧值。这段时间扫描和入队都不许再选它，否则同一条 VL 会连着发两帧，违反 BAG。tx_builder 只有一个“下一帧”位置，所以 `pend_vl` 一个寄存器就够。

**扫描的判断**（对 `scan_ptr` 指向的 VL）：

- `d = now − next_time`。`d` 不为负，说明间隔已到。
- `soon` = `timer_active` 为 0，或 `d + LOOKAHEAD` 不为负。`LOOKAHEAD = 512` 个周期，意思是“512 个周期内就到”。
- 有消息在排队、`soon` 成立、不是 `pend_vl`：定为候选。
- 没有消息在排队，`timer_active` 为 1 且间隔已到：把 `timer_active` 写回 0。这一步防止计数器回绕后误判，不能提前做。
- 然后 `scan_ptr` 加 1，到最后一条回 0。找到候选后扫描停在下一条，下次从那里接着找，所以各 VL 轮流，不会饿死。

**扫描的节拍。** 读一条 VL 要经过“给地址、RAM 输出、进寄存器、相减、判断”几拍，所以做成流水：每 2 个周期给出一个新地址，结果依次出来。别的操作写了 `tx_state` 的某条 VL，而这条 VL 正在流水里还没出结果，它的结果作废，要重新看。没有别的操作打断时，128 条看一遍不超过 300 个周期。

**扫描的进度保证。** 不管应用送消息多快，只要没有候选，任何一条 VL 相邻两次被看到的间隔不超过 400 个周期。这是“提前选、到点发”成立的前提：一条 VL 进入 512 个周期的窗口后，最晚 400 个周期被选中，再用不到 60 个周期授权和准备，赶得上到点起始。做法自己定，例如让扫描在别的操作期间只暂停、不从头重来，或者规定两次入队之间至少看过 16 条 VL（入队的回答和 `m_ready` 允许为此多等，但仍受“回答不超过 64 个周期”和第 5.2 节“96 个周期”的限制）。

**为什么要“提前选、到点发”。** 提前 512 周期选出即将到点的 VL，预备帧头，在 `now` 到达允许时刻时发送，满载长帧的实测发送抖动为 0。512 已大于 84 拍最短帧时隙；提前选中的 VL 尚未到期时会占住唯一候选槽，让其他已到期小帧等待。T16 保留该调度以维持原轮询与 BAG 行为，混合小帧的额外空等在 PROBE_T16 单独报告，不保证任意小帧组合都跑满线速。

交给 tx_builder 的字段：两网启用位、VLID、源 IP、目的 IP、源端口、目的端口（`port_en` 为 1 用消息带的，否则用默认的）、长度 n、SN、首页号、允许起始的时刻（`timer_active` 为 1 时是 `next_time`，否则是“立即”）。

### 5.4 tx_builder：组帧

tx_builder 里最多同时有两帧：一帧正在往 mac_tx 送字节，一帧在“下一帧”位置上准备和等待。

- **准备。** 收到授权后算好各长度字段，顺序累加算出 IP 头校验和，把 42 个字节的帧头备好。IP 头的“标识”字段用一个 16 位计数器，每授权一帧加 1，复位后从 0 开始。准备不超过 32 个周期。
- **起始。** 记允许时刻为 T；线路空闲且提前准备完成时，第一前导字节恰在 T 出现，不再取 8 拍边界。`now` 先寄存、差值再寄存，按原生 MAC 实测校准的 4 拍提前门槛置 `s_valid`；不把它当作线上起点，起点以 `tx_sof` 记录为准。T 已过去或允许“立即”时，准备完成即请求发送；前一帧字节未取完前不覆盖，MAC 在帧间隔满足后起始。
- **起始确认。** `tx_sof` 那一拍的 `now` 就是 `t_start`，报给 tx_engine；“下一帧”位置从这一拍起空出来。
- **发送中。** `s_valid` 到 `s_last` 被取走期间保持为 1，每次握手送出一个字节。42 字节头部发送期间开始预读载荷：注册请求、同步 RAM、RAM 输出寄存器及对齐流水把字节送进 8 项 FIFO，随后每拍补入、每拍取出。当前页与预读下一页号分开保存，跨页连续发请求。页末字节进入 FIFO、页链已读出后才归还该页；4 项归还 FIFO 加一个握手保持寄存器接住相邻周期的页末和消息末归还，避免 257/513 字节等边界漏页。顺序仍是帧头、n 字节载荷、不足 17 字节补 0、带 `s_last` 的 SN。
- **两网。** A、B 两路共用这一套逻辑，只在第 11 字节给出不同的值（`20` 和 `40`）。`s_en_a`、`s_en_b` 来自这条 VL 的 `net_a`、`net_b`。
- **帧头的做法（建议）。** 准备好的各字段和校验和放在“下一帧”位置的寄存器里；起始时把 42 个字节并行装进一个移位寄存器，发送时每个字节时间移一个字节，输出口上没有宽的多路选择。前一帧的帧头这时早已发完（任何一帧都不短于 60 个字节），所以一个移位寄存器够用。
- 统计用的单周期脉冲：`ev_tx_a`、`ev_tx_b`，一帧在 A 网、B 网上正常发完（`tx_eof`，且没有欠载）时给，不晚于帧结束后 16 个周期。

线路空闲、tx_builder 里没有别的帧、这条 VL 的间隔已到时，从消息的最后一个字节被收下到帧开始发送（`tx_sof`），不超过 100 个周期。

### 5.5 mac_tx：双网发送 MAC

模块 `afdx_mac_tx`。一个状态机，两套 CRC 和输出寄存器，所以 A、B 两网天然同步。它是发送节拍的主人：上游只管备好字节，什么时候取由它定。

| 端口 | 方向 | 含义 |
|---|---|---|
| `clk`、`reset`、`byte_en` | 入 | |
| `s_valid` | 入 | 上游有一个字节在等 |
| `s_ready` | 出 | mac_tx 在这一拍取走这个字节。正常发送时只在 `byte_en` 为 1 的周期出现 |
| `s_data_a[7:0]`、`s_data_b[7:0]` | 入 | 这个字节在 A 网、B 网上的值 |
| `s_last` | 入 | 这是本帧在 FCS 之前的最后一个字节 |
| `s_en_a`、`s_en_b` | 入 | 本帧发不发 A 网、B 网，在起始那一拍取样 |
| `tx_sof` | 出 | 单周期脉冲：线上第一个前导字节的第一个周期 |
| `tx_eof` | 出 | 单周期脉冲：FCS 最后一个字节结束后的第一个周期 |
| `tx_underrun` | 出 | 单周期脉冲：发送途中上游没备好字节 |
| `tx_data_a[7:0]`、`tx_valid_a`、`tx_data_b[7:0]`、`tx_valid_b` | 出 | 线路，都是寄存器输出 |

行为。状态在 `byte_en=1` 时变化，顶层中它恒为 1；输出逐周期更新：

1. **起始。** 空闲、帧间隔已满足、`s_valid` 为 1：取样 `s_en_a`、`s_en_b`，开始发前导。这一拍不取走字节。
2. **前导。** 7 个 `55`、1 个 `D5`，每个保持 1 个周期。
3. **数据。** `D5` 周期取走第一个字节，之后每周期取一个，直到取走带 `s_last` 的字节。
4. **FCS。** 4 个字节，A、B 各算各的。
5. **帧间隔。** `tx_valid` 为 0 至少 12 个周期；上游一直有帧等候时恰为 12 个周期。
6. 没启用的那一网，整帧期间 `tx_valid` 和 `tx_data` 都保持 0。两网都没启用时照常走完整个节拍。空闲时 `tx_data` 为 0。
7. **欠载**（数据阶段该取字节时 `s_valid` 为 0）：给 `tx_underrun` 脉冲，接着发 4 个字节的错误 FCS（CRC 不取反），对端校验必然失败；然后把上游这一帧剩下的字节全部取走丢掉，直到带 `s_last` 的那个（这期间 `s_ready` 可以连续为 1），丢完之前不起始新帧。按设计欠载不会发生，这一条是保底。
8. mac_tx 不补齐短帧，也不检查长度。帧长由 tx_builder 保证。
9. `tx_sof`、`tx_eof` 每帧各给一次，欠载的帧（在 4 个错误 FCS 字节之后）和两网都没启用的帧也一样。
10. **复位。** 复位期间线路输出全为 0，状态回空闲；复位结束后先等满 12 个周期帧间隔，再允许首帧。

字节时间的编号（一个字节时间就是一个周期，L 是取走的字节数）：

| 字节时间 | 线上内容 | 本周期发生什么 |
|---|---|---|
| 起始前一个 | 空闲 | 判断起始，取样 `s_en_a`、`s_en_b` |
| 0–6 | `55` | |
| 7 | `D5` | 取走第 0 个字节 |
| 8 到 8+L−1 | 第 0 到第 L−1 个字节 | 取走下一个字节；取走带 `s_last` 的字节后不再取 |
| 之后 4 个 | FCS | |
| 再之后至少 12 个 | 空闲（帧间隔） | 第 12 个周期可判断下一帧起始 |

CRC32：反射多项式 `0xEDB88320`，初值全 1，结果取反后低字节先发；计算范围从目的 MAC 到 SN。做成组合逻辑模块 `afdx_crc32_d8`（输入 32 位当前值和 8 位数据，输出 32 位新值），发送和接收共用。它是纯组合逻辑，不受第 9 节第 9 条“输出来自寄存器”的约束。

### 5.6 发送核心的外壳

模块 `afdx_tx_core` 把 5.1 到 5.5 连起来，表的实例和读写口归属集中在外壳。参数仍为 `TX_PAGE_AW`、`TX_OFF_AW`、`LOOKAHEAD`。`now` 和 `byte_en` 是输入，正常工作只要求 `now` 每周期加 1、`byte_en` 恒为 1；暂置 0 的模块测试不代表另一种顶层速率。

| 端口 | 方向 | 含义 |
|---|---|---|
| `clk`、`reset` | 入 | |
| `now[31:0]`、`byte_en` | 入 | 来自 `afdx_timebase` |
| `m_valid`、`m_data[7:0]`、`m_last`、`m_vl[6:0]`、`m_port_en`、`m_sport[15:0]`、`m_dport[15:0]` | 入 | 消息接口 |
| `m_ready` | 出 | |
| `cfg_we`、`cfg_addr[9:0]`、`cfg_wdata[31:0]` | 入 | 写 `tx_cfg`；清表完成前不接受；`cfg_we` 和 `cfg_ok` 同拍为 1 才接受 |
| `user_id[15:0]` | 入 | 端系统用户 ID，填进源 MAC 的第 9、10 字节 |
| `tx_data_a[7:0]`、`tx_valid_a`、`tx_data_b[7:0]`、`tx_valid_b` | 出 | 线路 |
| `init_done` | 出 | 清表完成（`tx_state`、`tx_cfg` 清零，空闲页装好），复位结束后 2048 个周期以内变 1。之前 `m_ready` 为 0，线路空闲 |
| `ev_accept`、`ev_drop_dis`、`ev_drop_full`、`ev_drop_long`、`ev_drop_nopage`、`ev_tx_a`、`ev_tx_b` | 出 | 统计脉冲 |
| `cfg_ok` | 出 | 这一拍引擎不会发出 `tx_cfg` 的读；配置写握手，组合定义见第 7 节 |

## 6. 接收侧

```
A 网 ──► mac_rx ──► rx_parse ──► 环形缓冲 A ─┐
B 网 ──► mac_rx ──► rx_parse ──► 环形缓冲 B ─┤
                        │ 帧描述              ▼
                        └────► rx_engine ──► rx_deliver ──► 应用 / 服务
                      （VLID 映射表、VL 状态表）
```

### 6.1 表

| 表 | 深度×位宽 | 写口归谁 | 读口归谁 | 内容 |
|---|---|---|---|---|
| `rx_map` | 65536×13 | 配置总线（清表期间归初始化状态机） | rx_engine | 用 16 位 VLID 直接查：`valid`[12]、接收 VL 序号 `idx`[11:0]。任意 4096 个 VLID 都能配 |
| `rx_cfg` | 4096×32 | 同上 | rx_engine | `en`[0]、`net_a`[1]、`net_b`[2]、`ic_en`[3]、`rm_en`[4]、`skew_max`[16:5]（单位 32.768 µs）、`max_payload`[27:17] |
| `rx_state` | 4096×44 | rx_engine | rx_engine | `psn_a_valid`、`psn_a`[7:0]、`psn_b_valid`、`psn_b`[7:0]、`rm_time_valid`、`rm_last`[7:0]、`rm_time`[15:0]，另有 1 位保留 |
| `rx_ring_a`、`rx_ring_b` | 4096×8 | 各自的 rx_parse | rx_deliver | 每网一个环形缓冲，按到达顺序存应用数据。地址位宽是参数 `RX_RING_AW = 12` |
| `rx_dq` | 32 项寄存器组 | rx_engine | rx_deliver | 待交付的网、起点、长度、idx、UDP 端口；默认 `RX_DQ_AW=5`，支持 1 到 5；队头先四组各 8 选 1，再注册后 4 选 1，仍是两拍 |

**环形缓冲的容量和剩余空间。** 每个环形缓冲正好能放 2^`RX_RING_AW` 个字节（读、写指针各多一位，用来分清空和满）。指针有三个：读指针归 rx_deliver，每读出一个字节加 1；“已提交的写指针”和“试写的写指针”归本网的 rx_parse。剩余空间 = 容量 −（已提交的写指针 − 读指针），正在收的这一帧不算在里面。

**`rx_dq`** 先进先出。rx_engine 决定交付时放进一项；rx_deliver 开始交付一条消息时把这一项取走，位置随即空出来，取走发生在这条消息第一个 `d_valid` 之前 8 个周期以内。

`rx_map` 用一个 65536×13 的 `afdx_ram_sdp`，读出后直接进一级寄存器，中间不接任何逻辑；从给出地址到结果可用是 2 拍。T1 实测：写成一个数组和拆成 16 块都占 208 个块；一个数组的写法少用约 200 个逻辑单元，未布线估算的 setup 裕量 6.09 ns，够用，所以不拆。退路（块 RAM 不够时才用）：用 VLID 低 12 位做下标、高 4 位做校验。

### 6.2 mac_rx（每网一个）

模块 `afdx_mac_rx` 不用 `byte_en`，把 GMII 输入打一拍后在每个有效周期处理一个字节，包括上升沿出现的第一个字节。

| 端口 | 方向 | 含义 |
|---|---|---|
| `clk`、`reset` | 入 | |
| `rx_data[7:0]`、`rx_valid` | 入 | 线路，进模块后先打一拍 |
| `m_valid` | 出 | 单周期脉冲：输出一个帧字节 |
| `m_data[7:0]` | 出 | 帧字节，从目的 MAC 的第一个字节到 SN，不含前导和 FCS |
| `m_first` | 出 | 和一帧的第一个字节同时为 1 |
| `f_end` | 出 | 单周期脉冲：一帧结束，下面两个信号在这一拍有效 |
| `f_err[1:0]` | 出 | 0 完好；1 FCS 错；2 帧长错；3 前导错 |
| `f_len[10:0]` | 出 | 含 FCS 的帧长；超过 1518 时固定给 1519 |

行为：

1. 空闲时等 `rx_valid` 由 0 变 1。复位后如果 `rx_valid` 已经是 1，先等它回 0，不从半截帧开始收。
2. 不再计 8 拍相位或取字节中点；`rx_valid` 为 1 的每个注册周期都处理一个字节。
3. **找帧起始符。** 取到 `55` 继续等；取到 `D5`，下一个取到的就是帧的第一个字节。`D5` 之前的 `55` 可以是任意个，包括 0 个。取到别的值，或者还没见到 `D5` 时 `rx_valid` 就回 0，是前导错。
4. **帧字节。** 每取一个字节都累加 CRC 和帧长。输出比输入晚 4 个字节：取到第 k+4 个字节时输出第 k 个，这样最后 4 个字节（FCS）不会输出给后级。
5. **帧结束。** 注册的 `rx_valid` 首次为 0 即结束，给 `f_end`。按顺序判：前导错；含 FCS 的帧长不在 64 到 1518 之间则帧长错；CRC（不取反）不等于 `0xDEBB20E3` 则 FCS 错；否则完好。帧长是 `D5` 之后的有效字节数。
6. **超长。** 一帧最多输出 1514 个字节，之后不再输出，继续等 `rx_valid` 回 0，按帧长错结束。
7. 前导错的帧不输出任何字节，等 `rx_valid` 回 0 后给 `f_end`，`f_len` 为 0。
8. `f_end` 至少比本帧最后一个 `m_valid` 晚 1 周期；之后立即回空闲，输入两帧间只有 1 个低周期也能接上。
9. `rx_valid` 为 0 时 `rx_data` 上的值一律不看。

### 6.3 rx_parse（每网一个）

按字节位置边收边处理，不保存整个帧头。

1. **检查帧头。** 下面任何一条不满足都算“帧头错”：
   - 第 0–3 字节是 `03 00 00 00`；第 12–13 字节是 `08 00`；第 14 字节是 `45`；第 23 字节（协议）是 `11`。
   - 第 20–21 字节：MF 位为 0、片偏移为 0（DF 位不管）。
   - IP 头校验和：10 个 16 位字顺序累加，进位回卷，结果应为 `FFFF`。
   - 记 n = UDP 长度（第 38–39 字节）− 8。要求 1 ≤ n ≤ 1471，IP 总长度（第 16–17 字节）等于 n + 28。
   - 帧结束时，含 FCS 的帧长 `f_len` 等于 47 + max(n, 17)。
   - UDP 校验和（第 40–41 字节）不为 0 时核对：伪头（源 IP、目的 IP、`0011`、UDP 长度）、UDP 头的 4 个字（校验和字段也在内）、n 个字节的数据（n 为奇数时末尾补一个 0 字节）按 16 位字累加，进位回卷，结果应为 `FFFF`。为 0 时不核对。补 0 的填充字节和 SN 不参加累加。
   - 除了上面这几条，别的都不查。特别是 n 小于 17 时的填充字节：发送侧填 0，接收侧不看它的值，不为 0 也不算错。
2. **记录。** VLID（第 4–5 字节）、源端口（34–35）、目的端口（36–37）、n、SN（第 42 + max(n, 17) 字节）。
3. **存数据。** 第 42 到 41+n 字节写入本网的环形缓冲，先不生效。第 42 字节到来之前 n 已经知道：第 42 字节到来的那一拍，环形缓冲的剩余空间（算法见第 6.1 节）小于 n，本帧就不写，记“溢出”。因为 mac_rx 的输出比线路晚 4 个字节，这一拍落在帧的第 46 个字节（从目的 MAC 数起，第一个算第 0 个）开始出现在线上之后 16 个周期以内。
4. **定类别。** 每个 `f_end` 定一次。先看 mac_rx 给的 `f_err`：1 是 FCS 错；2 或 3 是帧长错（前导错也算在这里）。`f_err` 为 0 时再按顺序看：帧头错；溢出；完好。类别脉冲（第 6.4 节末尾）由 rx_parse 自己给，在 `f_end` 之后 8 个周期以内。类别不是完好的，rx_parse 自己把写指针退回本帧开始前的位置，不交给 rx_engine。这样线上来多密的坏帧都不会漏计，rx_engine 也只需要处理完好帧。
5. **交出帧描述（只有完好帧）。** 从 `f_end` 到给出帧描述的拍数固定，与帧的内容无关（两个 rx_parse 是同一个模块，所以两网在同一拍结束的完好帧，帧描述也在同一拍给出）。给出后保持到 rx_engine 取走。内容：VLID、SN、源端口、目的端口、n、数据在环形缓冲里的起始位置、`f_end` 那一拍的 `now_c`。
6. **提交或回退。** rx_engine 决定交付时写指针生效，丢弃时回到本帧开始前。UDP 长度在第 39 字节收全，接着两拍计算 n、结束位置和空间限额，覆盖第 40–42 字节连续到达；UDP 累加的两级折叠在 `f_end` 后 `finish_phase=1` 核对、下一拍定类别，避免末载荷的折叠结果尚未有效。最短帧、奇数长度与非零 UDP 好/错校验均保留回归。
7. **不理的帧。** 第一个前导字节出现在 `init_done` 变 1 之前的帧，整帧不理：不给帧描述，不计数。

### 6.4 rx_engine：`rx_state` 的唯一主人

一次只做一件事：处理一份帧描述（只有完好帧才有），或者做一步老化。帧描述按交出的先后处理；两网在同一拍交出，先处理 A 网的。两网交出的时刻相差不到 16 个周期、又不在同一拍时，哪一份先处理不作规定（rx_engine 可能正在做一步老化）。

“到达时刻”是 `f_end` 那一拍的 `now_c`。`f_end` 在帧的最后一个字节离开线路之后 16 个周期以内给出。

处理一份帧描述的步骤：

1. 帧描述只来自完好帧；“完好帧”的类别脉冲 rx_parse 已经给过，这里不再计。
2. 查 `rx_map[VLID]`。无效：计“未知 VL”，回退，结束。
3. 读 `rx_cfg[idx]`、`rx_state[idx]`。VL 未启用、这一网未启用、n 大于 `max_payload`：计“配置不允许”，回退，结束。
4. 完整性检查（`ic_en` 为 1 时才做），每网各查各的。记本网上一帧的序号为 PSN，下面任一条成立就通过：
   - 清表后本网第一次收到这条 VL 的帧；
   - SN 等于 0（对端复位了）；
   - SN 是 PSN 的下一个；
   - SN 是 PSN 的下下个（允许丢一帧）。

   “下一个”按 1 到 255 循环算，255 的下一个是 1，0 的下一个是 1。不管通过与否，都把本网的 PSN 更新为这次的 SN。不通过：计“完整性检查丢弃”，回退，结束。`ic_en` 为 0 时这一步整个跳过，PSN 不看也不改。
5. 冗余管理（`rm_en` 为 1 时才做；为 0 时通过上一步的帧全部交付，`rm_last`、`rm_time` 不看也不改），两网合在一起看，先到的有效帧胜出：
   - `rm_time_valid` 为 0，或者这一帧的到达时刻与 `rm_time` 的间隔已超过 `skew_max`：交付。两份可能逆序处理，16位相减为负时先取绝对值；在窗口内的同一SN仍只交付一次，`skew_max=0`的跨刻度份仍按超过窗口处理。
   - 否则，SN 与 `rm_last` 相同：是另一网的重复帧，丢弃，计“冗余管理丢弃”。
   - 否则，SN 为 0，或者 `rm_last` 为 0：交付。
   - 否则，把 1 到 255 看成一个环，SN 领先 `rm_last` 1 到 127 步：交付；其余：丢弃，计“冗余管理丢弃”。
6. 交付：`rx_dq` 已满时计“溢出”，回退，结束，`rm_last`、`rm_time` 不改（满不满看作出决定那一拍的项数）。否则提交环形缓冲，把帧登记进 `rx_dq`；`rm_en` 为 1 时再把 `rm_last` 记为这次的 SN，`rm_time` 记为到达时刻，`rm_time_valid` 置 1。
7. 第 4 步之后只要 `rx_state` 有变化就写回。

时限：从取走帧描述到决定仍不超过 64 周期，双网同拍结束的后处理份不晚于帧尾后 150 周期；两项都是检查上限，不是下一帧开始的等待要求。原“下一载荷至少晚 380 多拍”的慢线预算作废，逐拍通路依靠解析流水及引擎实际处理节拍完成提交/回退，连续短帧与双网并发由原 gap、溢出用例及系统高负载实测检查。

**老化。** `now_c` 每变一次，锁存一个待处理老化请求，在空闲时检查下一条 VL：`rm_time_valid` 为 1 且距 `rm_time` 已超过 0x4000 个单位（约 0.537 秒），就把 `rm_time_valid` 清 0。帧描述仍优先；被打断的同一项会重试，只有检查完成才推进扫描位置并清请求，忙时不再丢掉粗刻度变化。原生双网每网最短帧间隔84拍，处理两份最多26拍，足以在4096拍的粗刻度内完成一次老化；4096项约0.134秒轮一遍，记录会在约0.671秒内失效，早于16位时间差的半圈1.074秒。

生产时 `now_c` 每4096拍加1；测试可加速公开粗时间输入，但需保留每次加1和足够的扫描空档。冗余帧的间隔用16位有符号差的绝对值；老化检查仍用当前时间减记录时间的无符号差，按上述扫描界限避免旧记录混入负差。

统计用的单周期脉冲，A、B 各一组 `ev_a[7:0]`、`ev_b[7:0]`：位 0 完好帧，位 1 FCS 错，位 2 帧长错，位 3 帧头错，位 4 未知 VL，位 5 配置不允许，位 6 完整性检查丢弃，位 7 溢出。两网合计：`ev_rm_drop`、`ev_deliver`。

线上每一帧（一段连续的 `rx_valid` 为 1）在它那一网上恰好得到一个“类别脉冲”：完好帧、FCS 错、帧长错、帧头错、溢出（环形缓冲放不下）之一，由 rx_parse 给，在帧的最后一个字节离开线路之后 32 个周期以内。类别是完好帧的，再恰好得到一个“结果脉冲”：未知 VL、配置不允许、完整性检查丢弃、溢出（`rx_dq` 已满）、`ev_rm_drop`、`ev_deliver` 之一，由 rx_engine 给，在作出决定之后 8 个周期以内，并且晚于它的类别脉冲、不晚于帧的最后一个字节离开线路之后 150 个周期。位 7 是两处来源相或。

### 6.5 rx_deliver

从 `rx_dq` 按先后取一项，从对应的环形缓冲每周期读出一个字节送出，读过的空间随即释放（读指针前进发生在对应的 `d_valid` 之前 4 个周期以内）。一条消息的 n 个字节在连续的 n 个周期里送出，`d_valid` 中间不断，`d_last` 和最后一个字节同时为 1。输出接口不带反压：`d_valid`、`d_data[7:0]`、`d_last`、`d_vl[11:0]`、`d_sport[15:0]`、`d_dport[15:0]`、`d_net`（0 是 A 网，1 是 B 网）。后四个信号在一条消息期间保持不变。

交付通路每周期 1 字节，双网各可按 1 Gbit/s 到达。启用冗余去重的正常双份只交付一份；两个独立满速输入若都要交付，单个应用出口不能保证无积压，环或描述满仍按原溢出规则回退。默认 32 描述用于接住长载荷交付期间跟来的短帧，16 项曾在原 128 VL 突发中少一条，扩至 32 项后通过。线路空闲时帧尾到首个 `d_valid` 不超过 200 周期，前一消息未完时不晚于其末字节后 16 周期。

### 6.6 接收核心的外壳

模块 `afdx_rx_core` 把 6.1 到 6.5 的各部分连起来，测试只碰它的端口。接收侧的表都在这个外壳里实例化，读写口接到第 6.1 节写明的模块。参数：`RX_RING_AW`、`RX_DQ_AW`（改小是为了在仿真里测溢出）。

| 端口 | 方向 | 含义 |
|---|---|---|
| `clk`、`reset` | 入 | |
| `now_c[15:0]` | 入 | 来自 `afdx_timebase` |
| `rx_data_a[7:0]`、`rx_valid_a`、`rx_data_b[7:0]`、`rx_valid_b` | 入 | 线路 |
| `cfg_map_we`、`cfg_cfg_we`、`cfg_addr[15:0]`、`cfg_wdata[31:0]` | 入 | 写 `rx_map`（地址是 VLID）或 `rx_cfg`（地址是 `idx`）；清表完成前不接受；对应写使能和 `cfg_ok` 同拍为 1 才接受 |
| `d_valid`、`d_data[7:0]`、`d_last`、`d_vl[11:0]`、`d_sport[15:0]`、`d_dport[15:0]`、`d_net` | 出 | 交付 |
| `init_done` | 出 | 清表完成（`rx_map`、`rx_cfg`、`rx_state` 清零，65536 个周期）。之前线上来的帧一律不理，也不计数 |
| `ev_a[7:0]`、`ev_b[7:0]`、`ev_rm_drop`、`ev_deliver` | 出 | 统计脉冲 |

## 7. 配置总线、复位和统计

**J3 地址。** 取消“总使能”（每条 VL 自己有 `en`）。

| 地址 | 内容 |
|---|---|
| `0x00000` | VERSION，只读，`0xC3060000` |
| `0x00001` | STATUS，只读，位 0 是 `tx_ready`，其余为 0 |
| `0x00002` | USER_ID，可读写，位 15:0，复位值 0，接到发送核心的 `user_id` |
| `0x00040` 到 `0x00046` | 发送计数器，只读，依次是 accept、drop_dis、drop_full、drop_long、drop_nopage、tx_a、tx_b |
| `0x00048` 到 `0x0004F` | 接收 A 网计数器，只读，依次对应 `ev_a` 的位 0 到位 7 |
| `0x00050` 到 `0x00057` | 接收 B 网计数器，同上 |
| `0x00058`、`0x00059` | rm_drop、deliver |
| `0x0005A`、`0x0005B` | 接收适配 a_gdrop、b_gdrop，只读 |
| `0x00080` 到 `0x00FFF` | 留给 RTC 和服务，现在没有映射 |
| `0x01000 + vl×8 + w` | `tx_cfg`，只写 |
| `0x10000 + VLID` | `rx_map`，只写，数据取位 12:0 |
| `0x20000 + idx`（idx 小于 4096） | `rx_cfg`，只写 |

上表以外的地址都没有映射。译码：地址位 17:10 等于 `0000_0100` 是 `tx_cfg`；位 17:16 等于 `01` 是 `rx_map`；位 17:12 等于 `10_0000` 是 `rx_cfg`。

**J2 新模块 `afdx_cfg`。** 地址译码、寄存器、27 个计数器、读出、一个“待写”寄存器。输出都直接来自寄存器。总线时序（t 是周期号）：

- 写：`cfg_wr` 和 `cfg_ready` 在 t 拍同为 1 才接受；`cfg_ready` 为 0 时来的写不理，主机要重发。`cfg_ready` 直接来自寄存器。
  - 写三张表：t+1 拍起 `cfg_ready` 为 0，待写寄存器把写使能、地址、数据保持不变地送给核心；核心的 `cfg_ok` 为 1 的那一拍（记为 u，u ≥ t+1）算写进去，u+1 拍 `cfg_ready` 回到 1。不受阻时 u = t+1，`cfg_ready` 只低一拍。u − t 不超过 64。
  - 写寄存器、写没有映射的地址：当拍完成，`cfg_ready` 不变。写没有映射的地址没有任何效果。
  - `tx_ready` 为 0 期间 `cfg_ready` 为 0。
- 读：`cfg_rd` 在 t 拍为 1，则 t+2 拍 `cfg_rvalid` 为 1、`cfg_rdata` 有效；其余时候 `cfg_rvalid` 为 0。读不看 `cfg_ready`，复位结束后随时可读，可以每拍都读。表的地址和没有映射的地址读出 0。同一拍读、写同一个寄存器，读到旧值。读数据的多路选择分两拍（第 9 节第 6 条）。
- 计数器：32 位，计满回 0，只有复位清零。t 拍读到的值 = 对应的统计脉冲在 t−1 拍及以前出现的次数（自上次复位起）。

**J1 配置写怎样避开查表。** 不做旁路，只做“避开”。

- `afdx_tx_engine` 增加输出 `cfg_ok`，含义是“这一拍我不会发出 `tx_cfg` 的读”：`cfg_ok = enable && op==IDLE && !want_enq && !want_grant`。`afdx_rx_engine` 增加输出 `cfg_ok`，含义是“这一拍我不会发出 `rx_map`、`rx_cfg` 的读”：`cfg_ok = enable && (op==IDLE || op==AGE) && !desc_a_valid && !desc_b_valid`。
- 两个核心的外壳里，配置写的那一级寄存器只在 `cfg_ok` 为 1 时收下写：发送侧 `cfg_write <= cfg_we && cfg_ok`，接收侧 `map_we <= cfg_map_we && cfg_ok`、`cfg_we <= cfg_cfg_we && cfg_ok`。两个核心各增加一个输出端口 `cfg_ok`，放在端口表最后。从此核心的配置口是握手：写使能和 `cfg_ok` 同拍为 1 才算写进去。
- 道理：引擎的读使能寄存器和外壳的写使能寄存器在同一个时钟沿装入，下一拍才作用到 RAM。`cfg_ok` 为 1 的那一拍引擎不装读使能，所以下一拍 RAM 上只有写。
- `cfg_ok` 是组合信号，用到引擎自己的寄存器和兄弟模块直接来自寄存器的输出（入队请求、帧描述有效、`grant_ready`）。这是第 9 节第 9 条的一个例外，写进那一条。
- 等待上限仍是 64 个周期。Claude 的估算：发送侧最坏是 START、ENQ、GRANT 连着做，约 25 个周期；接收侧最坏是两网各来一帧，约 30 个周期。

一条 VL 的配置占几个字的（`tx_cfg` 一条 6 个字；接收侧 `rx_map`、`rx_cfg` 各一个字），改的时候先把它停用（`en` 写 0），写完其余的字再启用。

**复位后的清表。** 块 RAM 的内容不受复位影响，所以复位后收发两个核心各自把带“有效”或“启用”位的表写成 0：发送核心清 `tx_state`、`tx_cfg` 并装好空闲页，接收核心清 `rx_state`、`rx_cfg`、`rx_map`。设计不依赖块 RAM 的上电初值。最长的是 `rx_map`，65536 个周期（0.524288 ms）。两个核心的 `init_done` 相与后打一拍成为 `tx_ready`。应用须等 `tx_ready` 为 1 才送消息；`app_tx_ready` 直接接发送核心的 `m_ready`，不由两个核心的就绪信号门控。`cfg_ready` 在 `tx_ready` 为 0 时保持 0，不接受配置写；接收核心按第 6.3 节的初始化规则忽略清表完成前开始的帧。

**统计计数器**（32 位，放寄存器里）：

- 发送：收下的消息数、因 VL 未启用/队列满/超长/无空闲页而丢弃的消息数（四个分开计）、A 网发出帧数、B 网发出帧数。
- 接收，A、B 各一套：完好帧数、FCS 错、帧长错（前导错也计在这里）、帧头错（含校验和）、未知 VL、配置不允许、完整性检查丢弃、溢出（环形缓冲放不下，或 `rx_dq` 已满）。
- 接收，两网合计：冗余管理丢弃数、交付数。
- 保留 A/B 两个 gdrop 计数器及地址；顶层已无接收适配，输入脉冲恒为 0，复位后计数保持 0。输入超长帧转由 MAC/解析器记 len，环及描述溢出仍记 a/b_ovf。

六种故障注入各对应一个计数器：FCS 错、A/B 重复、乱序、超长、VLID 不对、IP/UDP 校验和错。

## 8. 服务通道、RTC 和 SNMP

本节扩展第 7 节的配置表与应用通路。`afdx_svc` 在应用口、RTC/SNMP/615A 三个服务口和原生收发核心之间按消息仲裁，GMII 无速率适配。服务协议、配置地址和 VERSION `0xC3110000` 沿用已验收版本，615A 具体范围见第 15 节。

### 8.1 服务通道端口与仲裁

应用口 `app_tx_*` 与核心 `m_*` 沿用第 2、5 节的 valid/ready、data、last、vl、port_en、sport、dport。三个服务发送口使用 `svc_tx_*` 打包总线：位组从低到高为 RTC、SNMP、615A；valid/ready/last/port_en 各 3 位，data 为 3×8 位，vl 为 3×7 位，sport/dport 各 3×16 位。

应用和三个服务按整条消息轮询，次序为应用、RTC、SNMP、615A。选中消息后保持到最后字节握手，消息内的停顿不允许别的来源插入；完成后从下一来源开始选择。有服务等待时，应用不会连续独占。没有服务发送时，应用数据和 ready 组合直通核心，不增加缓存和流水拍。

核心交付 `d_*` 同时广播至 `svc_rx_*`。服务用当前 UDP 目的端口产生 `svc_rx_claim[2:0]`，首字节的认领结果锁存到 last；任一服务认领的消息只送服务，应用 valid/last 为 0，其余消息原样送应用。服务不向交付口施加反压；各服务使用不同 UDP 端口。

### 8.2 RTC 时钟与配置

`afdx_rtc` 使用 clk/reset、端系统就绪 enable、配置读写、一个服务发送口和广播接收口。输出 tx_valid/data/last、tx_vl、tx_port；RTC 对源端口和目的端口都使用 tx_port，置 port_en=1。rx_claim 在服务启用且目的端口匹配时有效。

实时时钟为 32 位秒和 32 位纳秒；配置秒的起点为 2000-01-01 00:00:00 UTC，线上 NTP 秒加 3155673600，接收时减回该常数，均按 32 位自然回绕。每拍前进 8 ns，纳秒达到 1000000000 时向秒进位；复位为 0，服务停用时继续计时。写时间先写两个暂存字，再用 CTRL.load 一次装入。纳秒配置范围为 0 到 999999999；配置和模式切换在没有 RTC 消息在途时进行。读 SEC 时同时快照 NS，随后读 NS 得到同一时刻的纳秒；总线仍为第 7 节的两拍读出。

| 字地址 | 名称 | 读写与含义 |
|---|---|---|
| 0x00080 | CTRL | RW，位0启用、位1主端；写位2为1装入暂存时间，位2读0。复位0 |
| 0x00081 | PERIOD | RW，从端请求间隔，单位时钟周期，复位125000（1 ms） |
| 0x00082 | TX_VL | RW，发送VL索引，低7位，复位0；请求、回应各自用本端配置的VL |
| 0x00083 | UDP_PORT | RW，低16位，复位123 |
| 0x00084 | SEC | 写秒暂存值；读当前秒并快照纳秒 |
| 0x00085 | NS | 写纳秒暂存值；读上次SEC读出的纳秒快照 |
| 0x00086 | OFFSET_SEC | RO，最近偏差的有符号32位秒部分 |
| 0x00087 | OFFSET_NS | RO，最近偏差的非负纳秒余数，小于1000000000 |
| 0x00088 | SYNC_COUNT | RO，从端完成校时的次数；复位清0 |

偏差表示为 `signed(OFFSET_SEC)×1000000000 + OFFSET_NS` 纳秒，例如 −12 ns 表示为秒 −1、纳秒 999999988。计数器32位自然回绕。请求间隔从发起时计算；一个周期未收到有效回应，下周期用新的Transmit时间戳重发，直到校时成功。接收报文完成的当拍及校时计算期间不发新请求；请求发完后才接纳回应，避免重发期间秒和小数字段正在更新时误认旧时间戳，迟到的旧回应仍必须通过Originate与当前请求的逐位匹配。主端只回应，不定时请求；主端行为、48字节报文和校时算法不变，不增加认证或公网时间服务器选择逻辑。

### 8.3 报文与同步

使用 [RFC 4330](https://www.rfc-editor.org/rfc/rfc4330.html) 的48字节SNTPv4报文，请求和回应等长，所有多字节字段按高字节先发。发送t1/t3仍在该消息**首字节与发送核心成功握手**时采样；接收t2/t4仍在核心交付首字节时采样。时间戳为NTP的32位秒加32位二进制小数；发送握手后开始换算，在对应字段发出前完成，不预测等待时间。

| 字节 | 请求（从端） | 回应（主端） |
|---|---|---|
| 0 | 0x23：LI=0、VN=4、mode=3 | 0x24：LI=0、VN=4、mode=4 |
| 1 | stratum=0（请求不使用） | stratum=1，本地配置时钟为参考 |
| 2–3 | Poll=4、Precision=-26 | Poll=4、Precision=-26（约14.9 ns） |
| 4–11 | Root Delay、Root Dispersion 均0 | 同左，作为本地主参考 |
| 12–15 | 0 | Reference ID=`LOCL` |
| 16–23 | 0 | Reference Timestamp：最近一次配置装入的时间 |
| 24–31 | Originate=0 | 原请求的Transmit逐位原样复制 |
| 32–39 | Receive=0 | 主端收到请求的t2 |
| 40–47 | 从端发出请求的t1 | 主端发出回应的t3 |

双方UDP源/目的端口均为配置的UDP_PORT，默认123。Poll=4是服务器报告的最大间隔16秒；实际实验请求周期仍由原PERIOD控制，复位1 ms，测试0.5 ms。本卡保留该算法和实验周期，只实现标准报文及本地双端对时，不声称实现RFC第10节的公网客户端轮询策略。

`afdx_ntp_fraction`每次换算用32轮、每轮两拍：纳秒转小数逐位比较/减法计算`floor(ns×2^32/1000000000)`；小数转纳秒逐位加/右移，末轮四舍五入。每拍最多一级32位加减，无乘除法器；自身整纳秒时间戳往返得到原值。发送、接收/配置参考时刻各用一个编码器；从端依次解码回应的t2、t3，换算不改变t4的原采样值。

从端保存内部t1，用回应Originate与已发送的完整NTP Transmit相等确认对应请求，再计算`offset=((t2−t1)+(t3−t4))/2`，加到当前时钟。秒差、纳秒差分开计算，各拍最多一级32位算术；有符号右移除2，奇数秒折成500000000 ns，再规范化余数。应用偏差时仍补回原计算流水的32 ns，换算期间时钟正常前进，校时基于应用时的当前时钟。报文用12个32位字段的小寄存器组，发送字按8字/4字分组选择，再选字节；不新增块RAM。

`tb_sys_rtc`保留从端初始超前、落后、主从互换、停止后保持及双向用户竞争场景，空载每次同步完成和停止后的误差均不超过40 ns；用72组独立整数向量检查双向小数换算。GMII请求/回应转成`sntp_exchange.pcap`，参考工具解出版本、模式、全部时间戳并核对Originate原样回填。

### 8.4 SNMP 报文和端口

`afdx_snmp` 是服务口 2（打包下标 1）的简单网络管理协议（Simple Network Management Protocol，SNMP）代理。启用后认领 UDP 目的端口 161；回应源端口为 161、目的端口为请求源端口，使用配置的发送 VL。VL 的地址、最大载荷和双网使能沿用第 5、6 节的普通表项，管理端事先配置好两个方向的 VL。

线上的 UDP 载荷使用标准 ASN.1 基本编码规则（Basic Encoding Rules，BER）。支持 SNMPv1（version=0）和 v2c（version=1）的 GetRequest（A0）与 GetNextRequest（A1），以及下述 SetRequest（A3），回应为 GetResponse（A2），原样保留 request-id 和 community。消息依次包含 SEQUENCE、version INTEGER、community OCTET STRING、PDU；PDU 包含 request-id、error-status、error-index 和 VarBindList；一个 VarBind 包含 OBJECT IDENTIFIER 和值。长度支持短形式、81 和 82 的定长形式；不使用不定长。依据：[RFC 1157](https://www.rfc-editor.org/rfc/rfc1157.html)、[RFC 3416](https://www.rfc-editor.org/rfc/rfc3416.html)。

每个请求支持一个变量绑定；请求最长 256 字节、OID 内容最长 16 字节、community 为 1–16 字节。管理端每次等到回应或超时再发下一请求。Get 精确匹配标量 OID；GetNext 按解码后的数字子标识符逐个比较，返回严格大于请求 OID 的第一个对象，支持从 `1.3` 开始遍历全部对象。v1 查不到时 error-status=2（noSuchName）、error-index=1、值为 NULL；v2c Get 返回 noSuchObject（80 00），GetNext 末尾返回 endOfMibView（82 00），两者 error-status/index 均为 0，保留请求 OID。GetBulk等尚未支持的操作不回应；community 不符不回应并将 BAD_COMMUNITY 加一。请求计数对被认领消息的最后一字节加一，包含Set、错误community和不支持的操作。

请求和回应各用一块 256×8 的 `afdx_ram_sdp`，逐字节解析与组装，输出遵守服务口 valid/ready。启用、community、回应 VL 只在管理消息不在途时改写；复位或停用放弃当前处理。请求长度、单变量绑定和串行管理访问是本卡选择的能力范围，不实现GetBulk或多个请求排队；Set和Trap见8.8节。

### 8.7 SNMP 验证入口

`tb_sys_snmp` 用两个完整顶层及双网GMII直连，ES1应用口是管理端，ES2启用代理。`tools/snmp_ref.py` 用 pyasn1 0.4.8 的标准BER编码器生成请求、解码回应；不读取RTL。先发用户消息使计数器非零，随后对全部对象分别运行v1/v2c Get和v2c GetNext遍历，期间继续双向用户消息；验证三个指定错误场景和community配置。管理源端口和带符号request-id改变，回应必须跟随。

测试经公开配置总线持续读取当前对象；同地址读在代理采样拍合并，用0x97定位同拍总线值。字符串的四个只读字先读全，代理采样的首字也核对。`snmp_results.txt` 中 `D case sport dport length hex` 记录回应，`B case sample_cycle value` 记录同拍配置读，末尾另一次USER_ID查询先被主机其他地址读阻塞、释放后由代理独立读取，`S case sample_cycle value` 记录该静态值的事后总线核对，`DESC hex` 记录描述字符串，`BAD before after` 和 `U sent1 sent2 received1 received2` 记录错误与用户流量结果。线路文件 `manager_gmii.txt`、`agent_gmii.txt` 沿用第10节抓包格式；参考工具从真实帧去掉前导和FCS写成 `snmp_exchange.pcap`，读回Ethernet/IP/UDP后用pyasn1解码。结果在 `check_summary.json`，测试须 RESULT 和 CHECK 同时通过。T8只验证RTL和综合估算，不把它当作网表或外部实机联调结果。

### 8.8 Set与主动通知

**Set。** v1/v2c使用同一community同时授权读和写。唯一可写对象为USER_ID（P.2.0），类型沿用Gauge32（42），允许0–65535，对应顶层16位USER_ID。代理先检查OID和类型，再经配置总线写0x00002，写接受后读回配置值生成GetResponse；request-id、community、OID及成功写入的值与请求一致。错误回应保留请求的OID和值，不改变配置，error-index=1：只读或不存在对象为v1 noSuchName(2)、v2c notWritable(17)；类型不符为v1 badValue(3)、v2c wrongType(7)。Gauge32内容长度非法时为badValue/wrongLength(8)，值超出USER_ID范围时为badValue/wrongValue(10)。community不符仍静默并计数，Trap开着时另外通知认证失败。

**Trap。** 只发送SNMPv2-Trap（PDU=A7、version=1），不发送v1 Trap。UDP源161、目的162，沿用0x91配置的发送VL及其目的IP；使用当前配置community、request-id=0、error-status/index=0。Trap恰有两个变量绑定，依次为sysUpTime.0的TimeTicks值和snmpTrapOID.0（1.3.6.1.6.3.1.1.4.1.0）的OBJECT IDENTIFIER值。coldStart取1.3.6.1.6.3.1.1.5.1；authenticationFailure取1.3.6.1.6.3.1.1.5.5。报文及通知OID依据[RFC 3416 §4.2.6](https://www.rfc-editor.org/rfc/rfc3416.html#section-4.2.6)、[RFC 3418](https://datatracker.ietf.org/doc/html/rfc3418)。

代理ENABLE从0到1且TRAP_ENABLE已为1时登记coldStart；已认领请求的community不符且TRAP_ENABLE为1时登记authenticationFailure。事件先挂起，当前回应完成后共用原回应RAM和服务发送口组装Trap；sysUpTime在开始组装时采样。关Trap或停用代理会清除尚未开始的通知。每种事件一个挂起位，沿用单请求在途的管理访问约定；事件不产生回复或重试。完整Trap最后字节被发送核心接受时TRAPS_SENT加一、32位回绕，不把双网副本算两次。

`tb_sys_snmp_settrap`覆盖两版Set成功、随后Get和配置总线读回、只读/不存在对象和错误类型、错误community的Set不生效、两种通知及关闭时均不发送。两端同时交付用户消息，延后观察确认无Trap重发。`tools/snmp_ref.py settrap_vectors/settrap_check`使用标准BER生成和解码，输出的`snmp_set_trap.pcap`含真实GMII的Set请求、回应和coldStart。共享测试部件仅观察顶层端口；`T sequence delivery_now sport dport length hex`记录通知，`C case user_id traps_sent received_traps bad_community`记录每个请求后的配置值，其余记录沿用8.7节。原Get/GetNext回归扩展到36对象，原不支持操作用GetBulk验证。

## 9. 时序纪律

代码书写沿用赛题要求：端口、信号、寄存器使用小写，参数及状态常量使用大写；官方顶层名保留 `AFDX_top`。每个 RTL 模块开头用中文说明作用、主要接口和关键时序，状态机与 RAM 流水等不直观处保留简短注释。T10 整理未改名，接口和下列逻辑约束均不变。

1. 单时钟。
2. 逐条 VL 的数据只能放 RAM。不许用 `mem2reg`，不许出现按 VL 数展开的触发器阵列或并行比较。
3. 所有 RAM 只通过 `afdx_ram_sdp` 实例化，地址、写数据和使能直接来自寄存器；不另写存储器数组。小寄存器组在注释写清用途：载荷 FIFO 8 项、归还 FIFO 4 项、RX 描述默认 32 项，后者以四组 8 项分组选择，禁止展开逐 VL 状态。
4. RAM 读出的数据先进寄存器，再做加、减、比较。RAM 输出和这级寄存器之间最多放一级不超过 4 选 1 的选择。（T1 实测，未布线估算：RAM 读出到寄存器 2.7 ns；RAM 读出直接接 32 位减法 4.4 ns。）
5. 一拍最多一级 32 位算术。不用乘法器、除法器；地址用位拼接，不用乘法。
6. 多于 8 选 1 的多路选择分两拍。
7. 数据逐拍推进，不在两字节之间安排额外处理周期；RAM 和算术用寄存流水、帧头期间预读。元数据准备可以多拍，但不得使已开始的帧欠载。
8. 同一拍读写同一地址的结果视为不确定，设计不能依赖它。
9. 模块的输出直接来自寄存器。握手用的 `ready` 可以例外，但只能是本模块状态和 `byte_en` 的简单组合。模块输入到第一级寄存器之间不做 32 位算术。 `cfg_ok` 是另一个例外：它是组合信号，用到引擎自己的寄存器和兄弟模块直接来自寄存器的输出（入队请求、帧描述有效、`grant_ready`）；确切定义见第 7 节。
10. 综合为单个 125 MHz、8 ns 约束，setup 裕量不小于 2.0 ns；不添加 false path、多周期例外或虚假 I/O 预算。T16 全顶层实测 +2.749 ns；未布线且未提供外部 I/O 延迟，不能当作完整物理时序签核。
11. 未布线估算里，每个 RAM 切片都有一个 −0.068 ns 的 hold 违例。T2 查到的事实：违例的终点都是 RAM 写数据寄存器的输入，不是地址，也不是写使能；数据这一路是 0.696 ns（触发器输出 0.490，RAM 输入 0.206，走线按 0 算），时钟到 RAM 比到触发器晚 0.754 ns，保持要求 0.010 ns，所以差 0.068 ns。也就是说，这段走线只要有 0.07 ns 以上的延迟，违例就没有了。我仍然判断它是估算把走线当成 0 造成的，但 T2 没能证实：命令行的布局布线跑完了，布线延迟却没有导入时序分析（工具报 `route.dly.pb.tr.cfg` 版本错误），报告里走线延迟还是 0。证实之前照实报告：不算通过，也不拦后面的任务；T6 的一次布局布线结果见 PROBE_T6.md，不把估算当作物理时序签核。

## 10. 验证方法

1. **期望值来自独立的参考工具。** `tools/afdx_ref.py` 按第 3 节和第 6 节的规则生成标准帧（CRC 用 Python 标准库）和期望的收发结果。它不看 RTL。测试平台里不另写一套 CRC 或校验和来算期望值，期望值一律读参考工具生成的文件。结果和调度先后有关、事先算不出来的测试（比如多条 VL 抢线路），改为仿真后核对：测试平台把激励、被测模块的统计脉冲和线上的帧记成文本，参考工具读这些文本逐条核对，输出一行 `[CHECK] <名称> PASS|FAIL items=<n> errors=<m>`。这类测试要 `[RESULT]` 和 `[CHECK]` 两行都是 PASS 才算通过。
2. **测试平台只碰端口。** 模块级只看端口；系统级只看 `AFDX_top` 端口，另保留四条核心收发视图供原核对程序使用。当前这些视图与 GMII 直接对应；网表只比对 GMII、D 和 sys_events，不读取内部核心视图，见第 16 条。
3. **自动判定。** 每个测试最后输出一行：`[RESULT] <名称> PASS|FAIL checks=<n> errors=<m>`。
4. **每项功能至少一个正常用例、一个异常或边界用例。**
5. **双端系统对通。** 两个 `AFDX_top` 各自有独立复位，经过四条单向链路互连；网络模型可以加任意整数周期的固定延迟、整帧丢弃、指定字节异或、扣帧后重放、同网重放和插入参考工具生成的字节段。按第 10、12 条的有效份规则检查应有的交付条数、同一 VL 的消息序号不减，并按第 13 条测时延和抖动。模型检查 GMII 重放和插入与前后各段至少相隔 12 个周期；普通帧的固定延迟发生冲突时报平台错误，不自动排队改变延迟。
6. **抓包文件。** 测试平台里的线路监视器把线上的每一帧记成一行文本，四个字段用空格分开：`<网> <起始周期> <字节数> <十六进制串>`。网是 `A` 或 `B`；起始周期是第一个前导字节第一个周期的周期号（十进制，取测试平台自己的周期计数）；字节从第一个前导字节到 FCS 最后一个字节，每字节两位小写十六进制，连着写。参考工具把这个文件转成 pcap（去掉前导和 FCS，时间戳 = 起始周期 × 8 ns），可以用 Wireshark 打开核对以太网、IP、UDP 各层。
7. **需求对照表。** 赛题每条功能和指标对应到测试名和证据文件。
8. 没跑的不写通过；RTL 仿真通过不等于综合后仿真通过，分开记。
9. **事件记录。** 收发核心的测试除了抓包文本，还要写一份事件记录文本，仿真后核对用（参考工具用，Claude 另写的核对程序也用）。每行一个事件，字段用空格分开；周期号和抓包文本用同一个计数；除注明的以外，数值用十进制，十六进制一律小写、不带前缀。

   | 行 | 含义 |
   |---|---|
   | `G <周期> <名称> <值>` | 被测模块的一个参数（十进制），开始时每个参数记一行：发送核心记 `TX_PAGE_AW`、`TX_OFF_AW`、`LOOKAHEAD`，接收核心记 `RX_RING_AW`、`RX_DQ_AW` |
   | `P <周期> <名称>` | 测试从这一拍起进入一个新阶段。名称只用小写字母、数字和下划线，各阶段要查什么由任务卡规定 |
   | `Z <周期>` | `reset` 变 1 的第一个周期。这一拍起排队的消息作废；线上正在发的帧被截断，线路监视器不把这半帧记进抓包文本 |
   | `R <周期>` | 复位结束后的第一个周期。各表从这里起是全 0，配置要重新写 |
   | `I <周期>` | `init_done` 变 1 的第一个周期。只有接收核心的测试记 |
   | `N <周期> <now>` | 这一拍 `now` 的值（十六进制）。开始时记一行，测试平台让 `now` 跳变时再记一行 |
   | `K <周期> <now_c> <步长>` | 从这一拍起 `now_c` 等于这个值（十六进制），之后每过“步长”个周期加 1，直到下一行 `K` |
   | `C <周期> <表> <地址> <数据>` | 一次配置写入。表是 `tx`、`map`、`cfg` 之一，地址和数据是十六进制 |
   | `U <周期> <user_id>` | `user_id` 的值（十六进制），开始时记一行 |
   | `M <周期> <vl> <n> <port_en> <sport> <dport> <数据>` | 一条发送消息。周期是它最后一个字节被收下的那一拍；端口是十六进制；数据是 n 个字节连着写的十六进制 |
   | `D <周期> <网> <idx> <sport> <dport> <n> <数据>` | 一次交付。周期是第一个 `d_valid` 那一拍；网是 `A` 或 `B`；端口是十六进制 |
   | `E <周期> <名称>` | 一个统计脉冲。发送侧的名称：`accept`、`drop_dis`、`drop_full`、`drop_long`、`drop_nopage`、`tx_a`、`tx_b`。接收侧的名称：`a_good`、`a_fcs`、`a_len`、`a_hdr`、`a_unk`、`a_cfg`、`a_ic`、`a_ovf`（对应 `ev_a` 的位 0 到位 7），`b_` 开头的八个同理，另有 `rm_drop`、`deliver` |

   接收侧测试抓包是激励的原样记录，一段连续 `rx_valid` 为一行，不论是否为合法帧。原生每字节保持 1 个周期、两段之间至少 1 个低周期；原随机 load 保留绝对提供间隔，速率覆盖另看 sys_perf。`now_c` 仍由测试平台产生，开始、复位后、步长变化各记 `K`，除复位不跳变、步长不小于 16；复位打断的交付不记 `D` 行。

   文件名固定：事件记录 `events.txt`，抓包文本 `dump_a.txt`、`dump_b.txt`，都放在这次仿真的输出目录里。
10. **系统级记录和采样。**

**J6 系统测试的记录。** 一个周期计数贯穿所有文件。一次仿真的输出目录里：

- 四个子目录 `es1_tx`、`es1_rx`、`es2_tx`、`es2_rx` 各含 `events.txt`、`dump_a.txt`、`dump_b.txt`，字段格式与 T3/T4 保持；参考核对的帧时长与字节节拍更新为 1，不能沿用旧 8 拍时间常数。
  - `*_tx`：抓包为两条核心发送线，也是直接 GMII；事件仍有 `G`、`P`、`Z`、`R`、`N`、`C`（tx）、`U`、`M`、`E`（发送名称）。
  - `*_rx`：抓包为两条核心输入，与 GMII 接收直通；事件仍有 `G`、`P`、`Z`、`R`、`I`、`K`、`C`（map/cfg）、`D`、`E`（接收名称）。
  - `P` 行四个文件里都记。`N` 和 `K`：测试平台里给每个端系统放一个“影子” `afdx_timebase`，接同一个 `clk` 和 `reset`，从它读 `now`、`now_c`，不看顶层内部。每次复位结束各记一行。`K` 的步长是 4096。
  - `I`：`tx_ready` 变 1 的第一个周期。
  - `C` 的周期取 u（核心收下写的那一拍，等于 `cfg_ready` 回到 1 的那一拍减 1）。
  - `U`：每次复位结束记一行 0；写 USER_ID 时再记一行，周期取 t+1。
- `sys_events.txt`：总线上每一次读写（含读回的值、写等了几拍）、网络模型的每一个动作、阶段标记。格式你定，写进 `ARCH.md` 第 10 节。

   所有端口、影子时间基准和事件都在时钟上升沿、非阻塞赋值更新之前采样；激励在下降沿准备。全局周期从第一个上升沿记作 1，各文件同用这个周期。`N`、`K` 记录影子 `afdx_timebase` 当拍的值，不读顶层内部。`I` 取 `tx_ready` 第一次为 1 的周期；表写的 `C` 取 `cfg_ready` 再次为 1 的周期减 1，也就是核心收下写的 u。运行中原值重写只记总线 `W`，不记 `C`；T6 的新值 max_payload 受阻写保留 `W` 的重写标记 0 并记 `C`，完成后才发送验证新值的消息；USER_ID 的 `U` 取写接受 t+1。

   复位打断的发送或接收半帧均不进入相应抓包，复位打断的交付不记 `D`；复位结束后已在途的半帧，线路监视器和 MAC 都先等 `valid` 回 0。系统测试只在被复位端自身两条发送线路空闲、接收线上正在收帧时复位它。网络模型不随接收端复位清空在途帧，也不随发送端复位清空已保存的完整帧或重新编号。

   除专门的运行中原值重写及 T6 新值受阻写外，写表和 USER_ID 只在 GMII、核心视图均空闲、最近帧尾已超 200 拍、发送队列已空时进行；写完至少 16 拍才来帧或消息。`I` 后至少 64 拍才来帧，复位场景继续按初始化屏蔽跨清表输入；换阶段排空、结束至少 20000 拍无流量的规则保持。

11. **`sys_events.txt` 格式。** 每行一个事件，字段用空格分开；周期、端系统号、链路号、帧号、长度、延迟、重写标记均为十进制。端系统号是 1、2；链路号 0、1 是 ES1→ES2 的 A、B，2、3 是 ES2→ES1 的 A、B。源帧号按每条链路所有发送段从 1 顺序编号，包含后来被 drop、xor、hold 的帧；重放、插入不增加源帧号。表地址固定 5 位小写十六进制，32 位数据固定 8 位；异或掩码固定 2 位；均不带前缀。

   | 行 | 含义 |
   |---|---|
   | `G <周期> <参数名> <值>` | 周期 0 记录顶层六个参数，以及 CLOCK_NS=8、GMII_TX_DELAY=10688、GMII_RX_REPLAY_R=16 |
   | `P <周期> <阶段名>` | 与四份核心事件记录相同的阶段标记；界外阶段名含 `outside` |
   | `W <t> <端系统> <地址> <数据> <u> <重写>` | 总线接受写的周期 t、核心收下表写的周期 u；寄存器或未映射地址 u=t。重写为 1 表示运行中原值重写，否则为 0；表写等待为 u−t |
   | `Q <t> <端系统> <地址>` | 总线读请求 |
   | `V <周期> <端系统> <地址> <数据> <t>` | 读响应及对应请求 t，响应周期必须为 t+2 |
   | `L <周期> <链路> <延迟>` | 从此周期起首字节到达模型的新帧锁存该整数周期延迟；已经接收的帧不改延迟 |
   | `A <周期> <链路> <源帧号> <动作> <字节下标> <掩码>` | 给尚未开始的源帧指定 pass、drop、xor、hold；字节下标从第一个前导字节算 0；只有 xor 使用下标和掩码 |
   | `R <请求周期> <链路> <源帧号> <计划起点>` | 在线路空闲处重放已经完整保存的源帧原始字节，不继承该帧原先的 xor；实际起点必须等于计划起点 |
   | `J <请求周期> <链路> <计划起点> <字节数> <十六进制串>` | 在线路空闲处插入 GMII 字节，每拍一个；实际起点必须等于计划起点 |
   | `E <周期> <端系统> <名称>` | 只记录 a_gdrop、b_gdrop，不加入原核心 events.txt |
   | `F <周期> begin或end <阶段名>` | 稳定吞吐测量窗口的左闭右开边界，不停流、不排空暖机队列 |

   链路动作任务在下一个采样周期生效；模型给重放和插入预留空闲位置并记录计划起点，后来的普通帧若撞上该区间，判测试平台出错。`W` 在完成后写出，`D` 在整条消息完成后写出，所以核对程序按记录中的周期排序，不按文本行出现顺序推断先后。

12. **系统核对与有效份。** 仿真后依次对 `es1_tx`、`es2_tx` 跑原有发送核对，对 `es1_rx`、`es2_rx` 跑原有接收核对，再跑只读记录的系统核对。四项核心、系统和 GMII 共六行 `[CHECK]` 与 `[RESULT]` 都是 PASS 才算 RTL 通过；整顶层网表按第 16 条外部记录特例。系统核对检查 S1 应有几条交付、S2 同一 VL 的消息序号不减、S3/X3 对 GMII 发送抓包施加链路动作后与 GMII 接收抓包逐字节及周期相同、S4 计数器读值等于上次复位以来 t−1 及以前的统计脉冲数、S5 总线时序、S6 等待与接收时延。S1、S2 使用以下裁定：

**R1 一条消息应当有几条 `D`。** 代替 S1 里的“一条 `M` 至多对应一条 `D`”和 `tb_sys_delay` 里的“`D` 行里的网应当是先到的那一网”。“恰好一次”是两网时间差不超过 `skew_max` 时的性质；超过时，后到的一份按新帧交付（`ARCH.md` 第 6.4 节第 5 步），系统测试要如实测到。

- 一条得到 `accept` 的消息在每一网上各有一份帧。同时满足下面三条的叫“有效份”：
  1. 发送端这条 VL 启用了这一网，这份帧没有被链路动作丢掉、改动或扣下（只加延迟的不算动过）；
  2. 接收端 `rx_map` 里有这个 VLID，`rx_cfg` 里 `en` 为 1、这一网启用、n 不大于 `max_payload`；
  3. n 不大于接收端环形缓冲的容量。
- 应有的 `D` 条数：

  | 情况 | 条数 |
  |---|---|
  | 没有有效份 | 0 |
  | 接收端 `rm_en` 为 1，普通阶段 | 1 |
  | 接收端 `rm_en` 为 1，“界外”阶段 | 每个有效份 1 条 |
  | 接收端 `rm_en` 为 0 | 每个有效份 1 条 |

  任何情况下，同一网的同一份至多交付一次；每条 `D` 都要对得上一条 `accept` 的 `M`（这一句不变）。
- “界外”阶段只在 `tb_sys_delay` 里有，阶段标记里写明。这种阶段里，同一条 VL 相邻两条消息的间隔要大于两网延迟差加 10000 个周期，保证上一条消息后到的那一份先于下一条消息先到的那一份到达。不这样安排会乱序交付，那是 P7 在界外本来就不保证的，不测。
- 复位阶段（`tb_sys_reset`）不查“应有几条”，只查“每条 `D` 对得上一条 `M`”和“同一份至多交付一次”。
- 来自哪一网，只在没有链路动作的阶段和 `tb_sys_delay` 里查。只有一条 `D` 时，它来自帧尾先到的那个有效份；两份的帧尾在同一拍算 A 网；相差 1 到 15 拍的不查（第 6.4 节不作规定），测试避开这样的延迟差。有两条 `D` 时，它们的先后与两份帧尾的先后一致。
- 有链路动作的阶段只查条数，不查来自哪一网（那由接收核对按参考模型查）。设计阶段时避免“某一网上同一条 VL 连续两帧到不了 rx_engine”（连丢两帧、连坏两帧、连着两条溢出）：否则下一帧过不了完整性检查，上面的条数规则就不成立了。
- S2 相应改为：把每条 `D` 对到它的 `M` 上，同一条 VL 的 `D` 依次对应的 `M` 的序号不减。
- 界线两侧的两对：一对的两份到达时刻正好差 `skew_max` 个单位（应有 1 条 `D`），一对正好差 `skew_max` + 1 个单位（应有 2 条）。消息的时刻要选得让这四份帧的到达时刻都没有两可：接收核对对这两对的判定必须是唯一的，不能落进 `either`。

**R2 `tb_sys_ovf`。** 由 R1 的第 3 条解决：n 大于环形缓冲容量的消息没有有效份，应有 0 条 `D`。这个测试另外要守三条：只用这一种“必然溢出”的消息造溢出，不靠缓冲里有积压；两条这样的消息之间至少隔一条正常交付的短消息；接收端两网的 `ovf` 计数器各自增加的数目等于这一网上这种帧的个数。

13. **系统时延、抖动和上限。**

**J7 核心边界的时延和抖动**（S6 诊断口径；单位是周期，1 个周期 8 ns）。对每条交付了的消息：M 是它在发送端被收下的周期（`M` 行）；S 是载着它的帧在发送端线路上的起始周期；F 是被交付的那一份在接收端线路上结束的周期（起始周期 + 8 × 字节数）；D 是接收端 `D` 行的周期；P 是同一条 VL 上一帧的 S（没有上一帧就不算这一项）；BAG 是这条 VL 的 `bag`。

- 等待 W = S − max(P + BAG, M)，它就是这一帧的发送抖动。上限按 P7 的公式：5000 + 这个端系统所有已启用 VL 的 (20 + Lmax) × 8 之和，其中 Lmax = 47 + max(`max_payload`, 17)。
- 接收时延 = D − F，硬上限沿用 15000 个周期（现在是 120 µs）。
- 端到端 = D − M，只报告，不设统一上限（里面含 BAG 等待和链路延迟）。
- W 超出上限时不要改 RTL：把那一帧前后的情况写进摘要就行（提前选中的 VL 会让线路最多空等 512 个周期，理论上可以叠加，要不要处理由 Claude 定）。

**R3 W 超出 P7 公式上限时 S6 怎么判。** 分两档。

- P7 公式上限（J7 里的那个），超出不判 FAIL：S6 的 `[CHECK]` 行里报超出的条数（`w_over=N`），摘要第 6 部分逐条列出（哪个测试、哪个阶段、哪条 VL、W、上限、它前面是哪几帧），超出的多于 10 条时列最大的 10 条。N 不为 0 也算完成，不用停；要不要改调度由 Claude 定。
- N 不为 0 的测试，另外用参数 `LOOKAHEAD=128` 再跑一次（只改参数，不改 RTL，不进回归），两次的 W 最大值和 `w_over` 都写进摘要。这一次只取 S6 的数字，别的检查过不过照实写一句就行。
- 硬上限，超出判 FAIL：W 不超过 P7 公式上限的 4 倍；接收时延不超过 15000。硬上限取得很宽，只用来查出“某条 VL 长时间轮不到”这一类错。按现在的调度做法不会超出：轮流扫描；每帧之前线路最多空等 `LOOKAHEAD` 个周期；新消息入队时可以插到扫描前面，每扫 16 条最多插一次。
- 硬上限被超出时：先确认不是核对程序或测试平台的问题，再照实报告，不改调度。

14. **碰撞监视、记录稳定性和任务卡冲突。** `afdx_ram_sdp` 在仿真中检查同拍 `write_enable`、`read_enable` 均为 1 且地址相同的情况，输出 `** Error: [RAMCOLL]`，带层次路径、时间和地址；脚本见 `** Error:` 即失败。第 0 步已确认综合前端预定义 `SYNTHESIS`，监视用 `` `ifndef SYNTHESIS `` 包住，且两个 RAM 探针的综合网表须与添加前逐行相同（日期行除外）。

**R4 “43 个文件”是哪些。** `tb_tx_*`、`tb_rx_*` 共 13 次运行各 3 个，39 个；加上 `tb_mac_tx`、`tb_mac_loop` 的 4 个抓包。43 个都不许变。上文说成“T3、T4 的 43 个”不准确。

**R5 以后再遇到卡里自相矛盾的地方。** 不要停。按 `ARCH.md` 写明的行为来，取最贴近卡的原意的读法，继续做，把矛盾和你取的读法写进摘要第 10 部分。只有三种情况才停下来问：要改变 `ARCH.md` 写明的行为；要动不许碰的范围；卡里写明“结果不符就停”的地方。

15. **网表仿真要短。** 网表里每个 RAM 切片都是一个很慢的仿真模型。T2 实测：65536×13（208 个切片）的网表每秒只能仿真约 700 个周期，没有 RAM 的 MAC 网表每秒约 7000 个周期。所以带 RAM 的网表测试用专门的短场景，每个不超过 20 万个周期；完整的用例矩阵在 RTL 上跑，两者分开记。

16. **GMII 记录和独立核对。** 事件与抓包四字段格式保持；四个核心观察目录和 `es1/es2_gmii_tx/rx` 都按每拍一字节记录。X1 核对核心与 GMII 发送字节及起点完全相同（D=0）；X2 查连续 valid 与至少 12 拍间隔；X3 独立重建链路丢、改、扣、重放、插入及固定延迟；X4 查接收引脚直通、复位/初始化屏蔽及 gdrop 恒 0（R=0），不再推算适配环容量和八拍重放。原故障内容保留，原适配溢出长段现在由 MAC 精确记 len。正常验收不出现 RAMCOLL/GMIITX。

整顶层 `tb_sys_net` 只记录 GMII 抓包、D 和 sys_events；八份 GMII 文本、两份 D 行及 sys_events 与已通过六项核对的 RTL 逐字节相同，并复核外部链路变换。网表不打印不存在的四项内部核心、X1 或 X4 通过结果。复位打断的段沿用原监视器规则省略，待低电平后再认新段。

17. **GMII 性能指标（T16）。** `tb_sys_perf` 保留 A/B 双网、10 条 VL 单向与双向满载、轻载；新增 77/81 条 VL 双向，每条载荷 1471 字节，所有阶段 BAG=125000。各用 0、257 周期链路延迟，错开提交；两 BAG 暖机后测固定 21 ms，每网帧字节、UDP 与去重交付载荷分别裁窗计数。10 条保留 110 Mbps 门槛，77 条每方向不少于 900 Mbps，81 条只测只报；替代原 BAG=123040 的上限探针。已收下消息排空后逐条查一次交付、每 VL 顺序和字节一致。

发送四种 drop、两网 fcs/len/hdr/unk/cfg/ic/ovf 不增加，gdrop 固定 0，rm_drop 等于交付数，稳定窗口也单独查。T_tx=M 末字节至 GMII 首字节，T_rx=GMII 接收末字节至 D 末字节，T_e2e=M 末字节至 D 末字节减固定链路延迟；均报最大/平均值。T16 同固定负载工况另严格查原始 T_e2e≤207.784 µs、满载发送抖动为 0、轻载不超过 7 拍。既有 S6 的 BAG 等待与 P7 公式诊断保持，不能从上述原始时延中扣排队等待；界线两侧和 128 TX/4096 RX 配置仍由原系统用例核对。

轻载按 1、17、18、1471、511 字节各重复八条，双向各一 VL，提交间隔 150003 拍；每长度排空后换下一长度，链路为 0/257。发送和端到端抖动分别取同长度组的 max−min，保留输出间隔相对已收消息间隔的诊断，不把不同长度或应用主动等待混算。固定负载之间排空并静默一 BAG，消除上一工况的定时相位。无该静默的额外切换探针曾得 323.112 µs，不能声称任意换负载都满足 207.784 µs；集中释放另以 `tb_gbe_burst` 预装 77/81 条、同时解除 MAC 停顿测排队完成时间与各消息原始 M→D 时延，不混入错开提交表。

## 14. 原生 GMII 与容量边界

### 14.1 直接发送

`AFDX_top` 的 A/B GMII 直接来自 `afdx_tx_core` 的 MAC 寄存输出。前导、数据、FCS 每周期一个字节，帧间隔 12 拍；`tx_sof` 与 GMII 首字节同拍，已无固定 D、压缩 RAM 或到期队列。BAG 起点、发送抖动均以这一接口实测。

### 14.2 直接接收

A/B 输入直接进入 `afdx_rx_core`，每网 MAC 寄存输入、逐拍找 D5 和累计 CRC，并以四字节流水剥离 FCS。解析器把载荷试写本来的 4 KiB 环，通过检查才提交，失败回退；初始化屏蔽、坏帧优先级、完整性及冗余规则不变。已无整帧适配缓存、R、慢线重放或适配器容量丢弃；gdrop 端口与两个计数器保留且恒为 0。

### 14.3 容量与已测范围

77/81 条最长消息的同步预装只占 231/243 个发送页，均小于 256 页；逐帧交付仍每 VL 保序，跨 VL 按轮询，不要求全局入队顺序。接收去重后出口最多每拍一字节，不能保证两路独立非冗余满速输入同时无损；环和描述溢出仍有原回退与统计。32 项描述解决已测长帧后接短帧的排队，零丢失保证限于已测工况，不能沿用旧适配器的 1374 拍等待或 3054 字节容量证明。

T16 保留 32 项原场景、增测两种集中释放并跑五功能 RTL；完整综合网表验收留 T17。

## 15. 615A 加卸载目标与加载存储区

### 15.1 作用与支持范围

`afdx_615a` 是被加载的目标硬件，加载端经 UDP/TFTP 传来上传清单，目标主动读取头文件和数据文件，校验后把数据留在 RAM，加载端从状态文件得知成功或失败。它接 `afdx_svc` 第三个服务口，收发共用原生双网核心、直接进出 GMII；认领的报文不交应用口，普通用户消息继续共用轮询调度。VERSION 为 `0xC3110000`。

依据为本地《ARINC 615A-2002.pdf》所含 Supplement 2 第 6.3.3、6.3.4、6.4 节、[RFC 1350](https://www.rfc-editor.org/rfc/rfc1350.html)、[RFC 2347](https://www.rfc-editor.org/rfc/rfc2347.html) 和 [ARINC 665-1 原文镜像](https://pdfcoffee.com/arinc-665-1-loadable-sw-standards-pdf-free.html)第 2.2.3、4 节。T9c 按用户要求将协议文件默认版本改为 ASCII `A4`；第3、4版原文尚未取得，版本定义和文件格式参考 [Thomas Vogt 的 arinc-615a](https://git.thomas-vogt.de/avionics/arinc-615a)（MPL 2.0，提交 `7b806af231cab992b07edfa42e18250d32da18d5`）的 `Arinc615a.hpp`、`files/InitializationFile.hpp`、`files/upload/UploadOperationRequestFile.hpp`、`UploadOperationStatusFile.hpp`。该实现将第3、4版均定义为 `A4`，LUI/LUR/LUS 字段格式与第2版原文相同；只读参考，没有复制代码。多字节字段均为大端，目标标识固定为 `DEMC3_1`，制造商 DEM 为规范中的演示系统标识。

本次实现一次上传一个头文件、头文件列一个数据文件，加载区为 8192 字节；数据文件按 665-1 为偶数字节。LUR 上限 512 字节、LUH 上限 2048 字节；LUR 文件名/件号字段含 NUL，长度 2–64；数据文件名 1–63 字符。超出支持数量、容量或文件长度报告失败，不截断后报成功。介质定义卸载支持一个 RAM 文件 `MEMORY.BIN`，长度为最近一次成功上传的字节数；信息操作、操作员定义卸载和FIND不实现。LCI/LNO初始化读请求以状态1002拒绝，不进入LCL/LCS或LNL/LNA后续操作。WAIT、ABORT和整文件重试未实现。第3版新增的可选 TFTP `port`、`part number`、`checksum` 语义及协商未实现，状态码 `0004` 不使用；不声称实现第3、4版全部可选能力。

### 15.2 实际上传流程

1. 加载端 RRQ `DEMC3_1.LUI`，目标以 DATA1 返回 9 字节 LUI：长度、配置版本（复位 A4，可选 A3）、接受状态 0001、空描述；收到 ACK1 后继续。全部 LUS 使用同一配置版本，进行中不允许切换。
2. 目标以 WRQ `DEMC3_1.LUS`、DATA1 发初始状态 0001，清单传送阶段头文件数为 0。加载端分别 ACK0、ACK1。
3. 加载端 WRQ `DEMC3_1.LUR`，目标 ACK0，接收 DATA 并 ACK。LUR 含总长、版本、头文件数、头文件名、件号；A3 和 A4 均接受，与发送版本配置无关。其他版本按元数据不支持拒绝，原因码1、TFTP ERROR 1/`FAIL 1`、最终 LUS `1003`，不读取头文件或数据文件；完整收到且检查通过后才保存名称与件号。
4. 目标发 LUS 0002，然后 RRQ 清单给出的 LUH。头文件完整接收且校验通过后再发 LUS 0002，RRQ 头文件给出的数据文件。
5. 每个 DATA 块按顺序写入 RAM 并累计 CRC。首个满块写入后暂缓 ACK，先用独立传输端口发 LUS 数值进度，收到状态文件 ACK1 后再 ACK 数据块。两项传输的端口、块号分别保存，不重复写入重传的数据。
6. 短块或空块结束数据传送。长度和 CRC 均正确才 ACK 最后一块并发送 LUS 0003、比例 100；最终状态文件获得 ACK 后配置状态成为成功。内容损坏则发送 TFTP ERROR 与 LUS 1003，逐头文件状态 1007，并报告原因。

每次新 LUS 的 16 位 counter 加一，重传不加；进度为已写字节/预期总字节的整数百分数，成功前最多 99，比例字段为右对齐三位 ASCII。初始 LUS 无头文件条目，其余 LUS 含清单中的名称、件号、比例、状态及描述；异常描述为 `FAIL n`，n 对应配置原因码。exception timer 为 0，进行中 estimated time 为 FFFF，其他状态为 0。最大文件的停等传输期间仍在首块后报告进度，正常传输时间短于常规加载端状态超时。

### 15.3 TFTP 与文件检查

TFTP 实现 RRQ(1)、WRQ(2)、DATA(3)、ACK(4)、ERROR(5)，模式 octet、每块 512 字节、块号从 1 开始，WRQ 以 ACK0 建立传输。请求目的 UDP 端口取 REQUEST_PORT，复位为59（615A第5.3.2.3.2节）；双方随后使用各自的传输标识符（Transfer Identifier，TID），服务端首次回应使用新的 TID。目标 TID 从 0x8100 起按新传输递增；主文件和 LUS 各自保存 TID。上传数据长为 512 的整数倍时，必须再接收零字节 DATA；卸载数据为整数倍时，目标发送零字节末块并等待 ACK 后结束。

报文在RAM中保留到回应到达；TIMEOUT_CYCLES以125 MHz时钟周期为单位，复位250000000，即2秒（615A附件4第3.1节）。超时原样重发上一个请求、DATA或ACK；RETRY_LIMIT复位为1（附件4第3.2节），指初次尝试之外的重传次数，耗尽以原因5失败。每次新的报文交换重新计次数，初发加1次重传最多2次尝试；B7单独累计统计。仿真写超时250000（2 ms）和重传上限2，以短周期检查恢复与耗尽。重复 DATA 只重发 ACK，不重复写 RAM；ERROR 不重传，收到对端 ERROR 终止相应操作。忙时收到另一操作的初始化读请求，返回初始化文件状态1000及BUSY描述，保留原传输TID与重发缓冲；没有有效加载内容时LND以1000及NO DATA描述拒绝。非法文件名或模式错误发 ERROR 1 或 4；本地校验/传输失败发 ERROR 加原因描述（元数据原因1沿用 ERROR 1）。此配置针对两个 C3 端系统和本卡指定出错情况。

第6.4.1节的四种初始化文件为LCI、LUI、LND、LNO；其中LUI/LND正常接受，未实现操作的LCI/LNO读请求返回同名初始化文件（长度9、配置A3/A4版本、状态1002、描述长度0）。TFTP仍使用新的目标TID、DATA1和ACK1；拒绝不改变原操作状态、已加载字节或重发缓冲，不产生后续状态传输。无对应协议初始化文件的非法文件名和模式错误沿用TFTP ERROR。

RRQ/WRQ 的 `octet` 终止 NUL 后可携带 RFC 2347 的选项名/值字符串对；目标忽略所有选项，不返回 OACK，RRQ 直接返回 DATA1、WRQ 直接返回 ACK0，后续仍用512字节块和配置的 REQUEST_PORT。`blksize`、`port` 等不会改变块长或端口；第3版新增选项定义参照上述参考实现的 `tftp/Arinc615aOptions.hpp`，本次只兼容忽略，不实现选项语义。

LUH 支持 665-1 版本 8002：读取头文件字数、绝对数据列表指针、数据文件数、文件名、件号长度（用于跳过）、数据文件字数和 CRC-16。字数与绝对指针以 16 位字为单位，字符串填充到偶数字节。检查头文件实际长度、版本、列表数量、头文件 CRC 和完整数据文件长度/CRC；CRC 多项式 0x1021，最高位优先、初值 FFFF、无结果反转。头文件 CRC 覆盖除末尾 Header CRC 与 Load CRC 六字节之外的全部头文件；数据 CRC 覆盖全部数据。

其余头字段跳过：加载件号和硬件 ID 的匹配、支持文件、用户定义数据、扩展点、Load CRC-32，以及解压/解密。参考生成器仍生成有效 PN CC、Header CRC 和 Load CRC（头文件除最后四字节在先，再接数据文件）。这不是完整 665 装载兼容性声明。

### 15.4 配置和 RAM

以下为字地址，接在 SNMP 区之后。原两拍配置读协议不变；启用、TX_VL、请求端口、超时、重传上限和协议版本仅在非进行中状态可改。状态为失败时 RAM 可含部分或损坏内容，仅成功状态表示有效加载结果；没有非易失写入或执行程序的动作。

| 地址 | 名称 | 行为 |
|---|---|---|
| 0xB0 | ENABLE | bit0 启用，复位为 0 |
| 0xB1 | TX_VL | 低 7 位发送 VL，复位为 0 |
| 0xB2 | STATUS | bit1:0：0空闲、1进行中、2成功、3失败；bit15:8原因 |
| 0xB3 | LOADED_BYTES | 本次已写字节数；新 LUI 初始化为 0 |
| 0xB4 | MEMORY_ADDRESS | 读回字节地址，低 13 位 |
| 0xB5 | MEMORY_DATA | RAM 字节位于低 8 位；B4 写后等至少 4 拍再读；仅非进行中有效 |
| 0xB6 | LUS_COUNTER | 本次新 LUS 或 LNS 状态文件数，16 位回绕 |
| 0xB7 | RETRY_TOTAL | 复位以来超时重传次数，32 位回绕 |
| 0xB8 | REQUEST_PORT | RW，低16位，复位59；写0不改变，客户端初始请求和服务端认领共用 |
| 0xB9 | TIMEOUT_CYCLES | RW，32位时钟周期数，复位250000000（2秒）；写0不改变 |
| 0xBA | RETRY_LIMIT | RW，低8位，复位1；初次发送之外的重传次数，0表示不重传 |
| 0xBB | PROTOCOL_VERSION | RW，低16位ASCII，复位0x4134（A4）；只接受0x4133（A3）或0x4134（A4），其他值及进行中写入不改变 |

原因码：0无错误、1元数据不支持/无效、2容量或长度、3 CRC、4对端 TFTP ERROR/模式错误、5重传耗尽。每次新 LUI 清除上次上传状态和字节数；RAM 不清零，以字节数和成功状态界定有效内容。五块 RAM 分别存 RX 报文、TX/重传报文、LUR、LUH 和加载数据，均使用 `afdx_ram_sdp`，地址、使能、写数据先寄存，读数据再寄存后参与运算。

系统测试的615A服务VL配置双方单播IP（10.0.0.2与10.0.0.3），使标准TFTP请求/应答的反向IP会话及文件名可由Wireshark关联；直接核对真实GMII抓包，不重写抓包地址。用户及其他组播服务流量按第3节的224.224+VLID配置。完成后再考虑：第3版新增的可选 `port`、`part number`、`checksum` 协商及语义。


### 15.5 介质定义卸载

依据Supplement 2第6.3.4、6.4.1、6.4.6节与上述开源实现的DownloadOperationRequestFile、DownloadOperationStatusFile，字段相符。最近成功加载的RAM作为文件`MEMORY.BIN`提供；开始新上传会撤销旧有效长度，避免随后失败的部分覆盖被作为旧文件交付。卸载只读RAM，不改变LOADED_BYTES；配置STATUS描述本次操作的成功或失败。

1. 加载端RRQ `DEMC3_1.LND`，目标DATA1返回长度9、配置A3/A4版本、状态0001、空描述，收到ACK1后WRQ/DATA1发送初始LNS0001。
2. 加载端WRQ `DEMC3_1.LNR`，目标ACK0后接收列表、ACK1。LNR含总长、A3/A4版本、文件数1、含NUL文件名长度和文件名，全部文件名后是用户定义数据长度及数据；用户定义数据忽略。列表只接受`MEMORY.BIN`，不存在的文件以ERROR1/FAIL 1、最终LNS1003和文件状态1007拒绝，不发送数据文件WRQ。
3. 目标发LNS0002后主动WRQ `MEMORY.BIN`。加载端以新TID的ACK0回应；目标读取RAM，按512字节DATA块停等发送，只有对应ACK到达才累计已确认字节。首个满块获得ACK后发送一次数值进度LNS0002，再继续下一块。
4. 最后短块（长度为512整数倍时是空块）获得ACK后，目标LNS0003、ratio100和文件状态0003；最终LNS获得ACK后STATUS成功。单次ACK丢失重发同一DATA，重试耗尽以原因5、ERROR、LNS1003和文件状态1007结束。

LNS公共字段为总长、配置版本、全局状态、描述、counter、exception timer、estimated time、三位ASCII总ratio、文件数；每项只有含NUL文件名、文件状态和描述，不含LUS件号或逐文件ratio。counter由1起每份新LNS加1，重发不加；exception为0，进行中estimated为FFFF，其余为0。ratio按已确认字节计算，成功前最多99。初始LNS文件数0，列表处理后为1；LNR和LNS均按规范大端字段编码。

加载与卸载共用0xB8–0xBB的端口、超时、重试次数和版本配置，不能同时进行；忙时初始化拒绝不会覆盖正在等待ACK的报文。完成后再考虑：操作员定义卸载LNO/LNL/LNA；第3版可选TFTP选项的协商与语义。
