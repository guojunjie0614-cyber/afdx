## 有要求出处和事实证据的发现

1. **重：相差 8 ns 的冗余帧会重复交付。** 出处：赛题功能2；P7 §3.2.6.2.2 要求先到者胜出、重复份不交付。
    证据：`rtl/afdx_rx_engine.v:153–160,201,224–225,272`；`P tb_t19_rx`，`out/t19/evidence/probes_tb_t19_rx_simulation.log`。两网 FCS 均正确，B 先到；phase=5 却先处理 A，时间234后再处理 B的233，无符号差成为65535，同一 SN=6 交付两次；另有3组后到 A 胜出。
    后果：一条应用消息被执行两次，破坏高完整性；这不是超过 SkewMax 的重复份。修复量：约80–150行，到达顺序仲裁、时间差判定及跨粗计时边界回归。

2. **重：合法长短帧切换超过 P7 抖动上限。** 出处：P7 §§3.2.2–3.2.4.3，尤其固定500 µs上限；赛题第5页抖动指标。
    证据：`rtl/afdx_tx_engine.v:161–172,338–347`；`P tb_t19_jitter`，`out/t19/evidence/probes_tb_t19_jitter_simulation.log`。77条VL、BAG=125000拍，先各发17字节再排入1471字节，全部长消息在对应 BAG 到期前入队，MAC从未停顿；W=S−上一S−BAG最大110504拍=884.032 µs，34条超过500 µs，154/154消息交付。
    后果：“发送抖动0”只覆盖固定同长度工况，当前77 VL配置没有所需的最坏抖动保证。`tools/sys_ref.py:95–96,355` 也未采用500 µs上限，而以公式值4倍判失败。修复量：限制合规配置或重做调度并补硬断言，约2–5人日，须重新验证900 Mbps目标。

3. **重：SNTP 接受无效服务器时间并校时。** 出处：[RFC 4330 §5、§6](https://www.rfc-editor.org/rfc/rfc4330.html#section-5)，§5按[已核准勘误2263](https://www.rfc-editor.org/errata/eid2263)读取，不能把正常的 LI=0 当错误。
    证据：`rtl/afdx_rtc.v:242–253` 只检查版本、模式和请求时间戳；`P tb_t19_rtc`，`out/t19/evidence/probes_tb_t19_rtc_simulation.log`。Stratum=0、16和发送时间戳全0都令 SYNC_COUNT 增加；全0时间戳把原10秒校到3286777344秒。
    后果：未就绪或拒绝服务的时间源可破坏本地时间。修复量：约20–50行有效性检查及相应负例。

4. **重：错误来源端口的 TFTP ERROR 能终止合法传输。** 出处：[RFC 1350 §4](https://www.rfc-editor.org/rfc/rfc1350.html#section-4)：来源 TID 不符应拒绝并回ERROR 5，不能扰动原连接。
    证据：`rtl/afdx_615a.v:493–498` 未检查 `peer_sp`；`P tb_t19_tftp`，`out/t19/evidence/probes_tb_t19_tftp_simulation.log`。A3正常LUI连接的加载端为45000，45001发来的ERROR使STATUS=0x0403，并向合法加载端发送ERROR 4。
    后果：错投或旧连接报文能中止本次加载。修复量：约30–80行完整端口绑定、错误TID应答和连接保持测试。

5. **重：615A 的 WAIT、ABORT 被当成普通失败。** 出处：615A §§5.3.2.3.4–5.3.2.3.7、5.4.5.3，分别要求等待后重试及回送中止状态码。
    证据：`rtl/afdx_615a.v:493–498`；`P tb_t19_tftp`，同上日志。对状态WRQ回复合法 `WAIT:2` 后立即失败；回复 `ABORT:1004` 后也成为0x0403，不发送回显1004的状态文件。测试选择A3，与本地原文版本一致。
    后果：正常加载器的延后和取消流程不能互操作，加载器无法确认中止原因。修复量：约150–300行等待、重启传输及状态文件处理，加独立加载器测试。

6. **重：截断的 TFTP 请求能借用上次 RAM 内容被接受。** 出处：[RFC 1350 §§2、5](https://www.rfc-editor.org/rfc/rfc1350.html#section-5)，RRQ必须携带完整、以NUL结束的文件名和模式。
    证据：`rtl/afdx_615a.v:264–286,531–563` 保存长度却未用它限制名称/模式读取；`P tb_t19_tftp`，同上日志。先正常RRQ，再复位，只发送两字节 `00 01`，仍收到13字节LUI DATA1；名称和octet来自未清除的接收RAM。
    后果：不完整报文可意外启动新操作；控制寄存器复位不能弥补报文边界缺失。修复量：约30–80行长度与终止符检查，不必清零整块RAM。

7. **重：接收方没有目的 IP 与通信端口的过滤绑定。** 出处：P7 §§3.4.1.1、3.4.1.4.2、3.4.1.5，合法交付由MAC、IP、UDP目的地址及物理接口共同决定。
    证据：`rtl/afdx_rx_parse.v:144–169,196` 不比较或保留目的IP，`rtl/afdx_rx_engine.v:191–198` 只查VL使能、网络和长度；`P tb_t19_rx` 的case=1把VL100帧的组播IP改为VL101地址、重算校验后仍交付，日志同第1条。`rtl/AFDX_top.v:30–35` 也不把目的IP交给应用补查。
    后果：映射存在的VL可把不属于目标通信端口的报文交付，服务也仅按UDP端口认领。修复量：新增地址绑定与过滤配置、保留必要元数据，约150–300行及映射回归。

8. **重：正常的多变量 SNMP Get 被静默丢弃。** 出处：[RFC 1157 §4.1.2](https://www.rfc-editor.org/rfc/rfc1157.html#section-4.1.2)、[RFC 3416 §4.2.1](https://www.rfc-editor.org/rfc/rfc3416.html#section-4.2.1)，要求处理变量绑定列表并回应。
    证据：`rtl/afdx_snmp.v:477–486` 强制第一个绑定结束位置等于列表结束；`P tb_t19_snmp`，`out/t19/evidence/probes_tb_t19_snmp_simulation.log`。40字节单变量请求正常回应，54字节双变量请求在v1、v2c下均无回应，未超过256字节容量。
    后果：常见管理器一次读取多个对象会超时；不是只缺可选的大报文能力。修复量：约150–250行绑定迭代、应答长度及容量错误处理。

9. **重：SNTP 丢失一次回应后永久停止同步请求。** 出处：赛题功能5；[RFC 4330 §10步骤3](https://www.rfc-editor.org/rfc/rfc4330.html#section-10)规定无回应后的定时重试。
    证据：`rtl/afdx_rtc.v:230,327,341–344`，计数归零不清waiting，只有成功校时或复位/停用才清；`P tb_t19_rtc`，同第3条日志：丢首个回应后经过10个配置周期仍仅1次请求、0次同步。状态条件还能逐步推出继续等待任意久也不会重发。
    后果：正常网络丢包会使同步功能停住，必须人工复位或重启服务。修复量：约30–60行请求超时、退避及恢复回归。

10. **重：没有 P7 的8 KiB排队消息及IP分片重组。** 出处：P7 §§3.3.1.1.2、3.3.1.1.2.1–2；8 KiB指应用消息，多帧承载，不与1518字节帧上限冲突。
    证据：`rtl/afdx_tx_buf.v:156–162` 在第1472个输入字节转入丢弃；`rtl/afdx_rx_parse.v:149–150` 拒绝所有MF或非零片偏移。`P tb_t19_rx` 的case=5/6发送组成32字节UDP载荷的两个合法IP分片（偏移0/3、相隔超过1 ms），均记帧头错、无交付，日志同第1条。
    后果：即使缓冲尚有空间，也不能完成原文要求的排队消息通信。修复量：发送分片、接收重组及消息描述重构，约1–2人周。

11. **重：缺少采样端口的保存、重复读取和新鲜度语义。** 出处：P7 §§3.3.1.1、3.3.1.1.1.2，要求保留最近消息，供多个订阅分区读取，并提供新鲜度。
    证据：`rtl/afdx_rx_deliver.v:67–72,126–169` 在有描述时自动弹出并读完释放环空间；`rtl/AFDX_top.v:30–35` 只有单次推送，没有端口读取、重读或新鲜度接口。逐步结果是：消息到达→无条件输出→释放空间；应用稍后读取时没有完整消息或有效期可查询。
    后果：本仓库交付的是消息流，不能替代P7采样接收服务；不能假定另有未交付的软件补齐。修复量：增加端口存储和读接口，数百行，须重新核算容量。

12. **重：不支持 P7 明确要求的 ICMP Echo。** 出处：P7 §3.3.3.2及附件2印刷页113，Echo server行在AFDX的MUST列标X，已核对原页图像。
    证据：`rtl/afdx_rx_parse.v:151,195–209` 把所有IP协议号非17的帧标错并回退；合法Echo的协议号为1，因此不可能进入服务。`rtl/afdx_tx_builder.v:232–233` 又固定构造UDP头，没有Echo应答路径；此结论不依赖仿真。
    后果：标准诊断的单播Echo请求无应答。修复量：IP/ICMP分流、Echo编解码和应答配置，约2–4人日。

13. **重：615A 目标没有 FIND 发现服务。** 出处：615A §5.4.1要求目标实现FIND；附件3 §§1–4规定UDP1001的请求与回答。
    证据：`rtl/afdx_615a.v:104,486–498` 只认领TFTP请求/传输端口，`rtl/afdx_svc.v:109–126` 将其余UDP交应用；默认1001无人处理，也没有IAN生成状态。即使把请求端口改为1001，仍进入TFTP文件名解析，不能产生FIND回答。
    后果：使用FIND扫描的加载器发现不了本目标；附件2.2的静态配置加载路径仍可用，不把它误报成所有加载都失败。修复量：约100–200行UDP1001处理、设备标识及发现回归。

14. **中：RTC 原回归缺少请求关联的负例。** 出处：答疑R2/R46要求自编激励验证；RFC 4330 §5检查3要求回应Originate匹配请求Transmit。
    证据：副本仅删除 `rtl/afdx_rtc.v:249` 的时间戳匹配条件；执行 `& E:\anaconda3\python.exe -B out/t19/run_review.py test mutant_rtc --test tb_sys_rtc`，`out/t19/evidence/mutant_rtc_tb_sys_rtc_simulation.log` 仍PASS 10675857检查，外部检查也PASS 1811项；同副本运行 `tb_t19_rtc` 则因错误Originate被接受而FAIL。
    后果：34项中的这个用例不能检出丧失回应关联保护；未声称变体全34项已重跑。修复量：增加错误/旧Originate、无效服务器和丢包恢复激励，约50–100行。

15. **轻：SNMPv2c 把缺失实例报成缺失对象。** 出处：RFC 3416 §4.2.1(2)–(3)区分 `noSuchObject` 与 `noSuchInstance`。
    证据：`rtl/afdx_snmp.v:589–600` 的Get失败统一发0x80；`P tb_t19_snmp` 的case=2查询已有sysDescr对象的实例 `.1`，应回0x81，却回0x80，见 `out/t19/evidence/probes_tb_t19_snmp_simulation.log` 的原始BER。
    后果：管理器得到错误的对象存在性信息。修复量：约20–40行对象前缀/实例判断和一个负例。
