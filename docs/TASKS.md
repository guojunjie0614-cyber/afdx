## T1：脚手架、RAM 原语、工具链探测

**目的。** 建好 C3 的目录和统一的仿真、综合入口；确认 eLinx 怎样把 RAM 映射成块 RAM、速度如何。后面所有表都建立在这个结果上。

**限时。** 90 分钟。

**要做的：**

1. 建目录 `schemes/scheme_c3/`：`rtl/`、`tb/`、`tools/`、`sim/`、`elinx/`、`docs/`、`out/`，加 `.gitignore` 忽略 `out/`。`docs/` 里已有 `ARCH.md` 和 `TASKS.md`，一并提交，不要改内容。
2. `sim/run.ps1 -Test <测试模块名>`：编译 `rtl/*.v` 和对应的测试平台，命令行方式跑 ModelSim，日志写到 `out/`，把测试最后那行 `[RESULT] ...` 打印出来；通过返回 0，否则返回非 0。预留 `-Netlist <网表文件>` 参数（用网表代替 `rtl/*.v`，本卡可以先不实现，但要在帮助里写明未实现）。
3. `sim/regress.ps1`：按 `sim/tests.txt` 逐个跑，最后打印汇总表，有一个不过就返回非 0。
4. `elinx/synth.ps1 -Top <模块名> [-Sta]`：对 EQ6HL130（CSG484）综合，时钟约束 100 MHz，输出放 `out/`，最后打印一行汇总：逻辑单元数、块 RAM 数；带 `-Sta` 时再加最差裕量（或最高频率）和最差路径的起点、终点。可以借用 C_v2 已有脚本的做法。
5. `rtl/afdx_ram_sdp.v`：单时钟、一个写口、一个读口、同步读的 RAM，参数 `WIDTH`、`DEPTH`。按下面的模板写，这是 C_v2 里已经证明能推断成块 RAM 的写法：

   ```verilog
   reg [WIDTH-1:0] memory [0:DEPTH-1];
   always @(posedge clk)
       if (write_enable) memory[write_address] <= write_data;
   always @(posedge clk)
       if (read_enable) read_data <= memory[read_address];
   ```

6. `tb/tb_ram_sdp.v`：自动判定。正常用例：全地址写入后读出比对，读延迟正好 1 拍，`read_enable` 为 0 时输出保持。边界用例：最低和最高地址；写使能为 0 时内容不变。
7. 综合探测，小包装模块放 `elinx/probe/`，每项单独综合：

   | 编号 | 内容 | 要回答的问题 |
   |---|---|---|
   | P1 | `afdx_ram_sdp` 的四种规格：2048×8、128×32、4096×44、4096×13 | 是否映射成块 RAM，各用几块 |
   | P2 | 65536×13 写成一个数组 | 是否映射成块 RAM，用几块；地址寄存器 → RAM → 输出寄存器这条路在 100 MHz 下的裕量 |
   | P3 | 65536×13 拆成 16 个 4096×13，读出后先各自进寄存器，再 16 选 1，再进寄存器 | 块数和裕量，与 P2 比较 |
   | P4 | RAM 读出 → 寄存器 → 32 位减法 → 寄存器；以及 RAM 读出 → 32 位减法 → 寄存器 | 两种写法在 100 MHz 下各自的裕量 |
   | P5 | 带 `initial` 初值的 RAM（全 0，和用 `$readmemh` 装入） | eLinx 是接受、忽略还是报错 |

   某项跑不出时序数字时，写明卡在哪一步，不要硬凑。
8. `docs/PROBE_T1.md`（不超过 60 行）：一张结果表，数字从工具输出里抄，注明对应的日志文件名；再加复现用的命令。

## T2：MAC、CRC32、参考工具、网表仿真

**目的。** 做出线路层：把字节流装成带前导和 FCS 的线上帧，再从线上收回来。同时建好后面每张卡都要用的两样东西：独立的 Python 参考工具，和综合后网表的仿真入口。

**依据。** `ARCH.md` v0.2 的第 2 节（端口上的字节节拍）、第 3、4 节、第 5.5 节、第 6.2 节、第 9、10 节。动手前先读这几节。

**限时。** 180 分钟。A、B、C 必做，按这个顺序；D 放最后，最多用 30 分钟，做不完不影响本卡算完成。

### A. RTL、参考工具、测试

1. 四个模块，端口名和行为照 `ARCH.md`，不带参数：`rtl/afdx_crc32_d8.v`、`rtl/afdx_timebase.v`、`rtl/afdx_mac_tx.v`、`rtl/afdx_mac_rx.v`。
2. `tools/afdx_ref.py`，只用 Python 标准库，不看 RTL：
   - 函数：`build_frame`（按第 3 节生成从目的 MAC 到 SN 的一帧）、`fcs`（用 `zlib.crc32`，低字节在前）、`line_bytes`（前导 + 帧 + FCS）、IP 头校验和。
   - `selftest`：自检。至少包括：`123456789` 的 CRC32 是 `0xCBF43926`；一个已知答案的 IP 头校验和；n 取 1、17、18、1471 时含 FCS 的帧长是 64、64、65、1518；一帧连 FCS 一起算，不取反的 CRC 值是 `0xDEBB20E3`。
   - `vectors --test <测试名> --seed <数> --out <目录>`：生成该测试的激励和期望值。文件格式自己定，在脚本开头的注释里写明。同一个种子两次生成的文件必须相同。
   - `pcap --dump <抓包文本> --out <pcap 文件>`：读 `ARCH.md` 第 10 节第 6 条格式的抓包文本，逐帧核对前导、帧长、FCS，打印总帧数和各类坏帧数；好帧写成 pcap（链路类型 1，纳秒时间戳）。
3. 测试用的公共部件放 `tb/lib/`，`eda.py` 编译测试时一并带上：
   - 线路监视器：接在发送线路上。检查一帧占的周期数是 8 的倍数、每个字节在它的 8 个周期里不变；量出和上一帧之间 `tx_valid` 为 0 的周期数；把每一帧按第 10 节第 6 条的格式写进抓包文本。
   - 线路驱动器：往接收线路上播放一帧，每个字节保持 8 个周期。前导内容、帧前的空闲周期数（不必是 8 的倍数）、空闲时 `rx_data` 上放什么值，都由调用者给。
4. 三个测试，见下面三张表。期望值都读参考工具生成的文件，测试平台里不写 CRC。`sim/run.ps1` 跑测试前先调参考工具生成向量；向量放 `out/`，不进 git。

**`tb_mac_tx`**（被测：`afdx_mac_tx`；`byte_en` 由测试平台自己每 8 拍给一次）

| 用例 | 要检查的 |
|---|---|
| 帧长 64、65、100、1518 和随机长度，A、B 两路的字节不全相同 | 线上内容与期望逐字节相同，包括前导和两网各自的 FCS |
| 只发 A、只发 B、两网都发、都不发 | 没启用的一网整帧期间 `tx_valid`、`tx_data` 为 0；都不发时 `tx_sof`、`tx_eof` 照给，节拍不变 |
| 上游一直有帧在等 | 帧间隔正好 96 个周期；连发 64 字节帧时，相邻两帧的起点相隔 672 个周期 |
| 上游晚到：空闲很久才给、在帧间隔里给、`s_valid` 在任意相位变 1 | 起始只发生在字节边界上；帧间隔不小于 96 个周期 |
| 节拍 | `tx_sof` 在第一个前导字节的第一个周期；`tx_eof` 在 FCS 结束后的第一个周期；正常发送时 `s_ready` 只在 `byte_en` 的周期为 1，每个字节正好取一次；两网都发时 `tx_valid_a`、`tx_valid_b` 每个周期都相等 |
| 欠载，分别发生在第 0 个字节、中间、最后一个字节 | `tx_underrun` 给一个脉冲；线上是已发的字节加 4 个不取反的 CRC 字节；上游这一帧剩下的字节被取走丢掉；下一帧完好 |
| 发送中途复位 | 线路从下一个周期起为 0；复位结束后至少 96 个周期才起始；之后的帧完好 |

**`tb_mac_rx`**（被测：`afdx_mac_rx`）

| 用例 | 期望 |
|---|---|
| 完好帧：64、65、1518 和随机长度；帧前空闲 96 个周期、8 个周期、随机个周期（包括不是 8 的倍数的） | `f_err` 为 0，`f_len` 正确；输出字节与原帧相同，不含 FCS；`m_first` 只和第 0 个字节同时出现 |
| 前导：0 个、1 个、7 个、20 个 `55` 后接 `D5` | 都正常收 |
| 数据里翻转 1 位；FCS 里翻转 1 位 | `f_err` 为 1 |
| 短帧：`D5` 之后有 0、1、3、4、5、63 个字节 | `f_err` 为 2，`f_len` 等于实际字节数；输出字节数是帧长减 4，帧长不到 5 时不输出 |
| 长帧：1519、1600、3000 个字节 | `f_err` 为 2，`f_len` 为 1519，正好输出 1514 个字节 |
| 前导里出现别的值；还没见到 `D5` 时 `rx_valid` 就回 0 | `f_err` 为 3，`f_len` 为 0，不输出字节 |
| 每种坏帧后面紧跟一个完好帧，空闲 8 个周期和 96 个周期各试一次 | 完好帧正常收 |
| 空闲时 `rx_data` 上是随机值；复位结束时 `rx_valid` 正好为 1 | 不产生任何输出，直到下一个真正的帧起始 |
| 每一帧 | `f_end` 正好一次，并且晚于本帧最后一个 `m_valid` |

**`tb_mac_loop`**（被测：`afdx_timebase`、`afdx_mac_tx`、两个 `afdx_mac_rx`；发送的 A、B 线路分别接到两个接收）

- 至少 200 帧。帧长、两网是否启用、上游给帧的时刻都随机，其中要有一段连续背靠背的帧。
- 启用的一网：接收输出的字节与发送的相同，`f_err` 为 0。没启用的一网：没有任何输出。
- 两条线路都接监视器。仿真后把抓包文本转成 pcap，坏帧数必须是 0。

### B. 综合和时序

5. `afdx_timebase`、`afdx_mac_tx`、`afdx_mac_rx` 各综合一次并做 100 MHz 时序估算，得到的网表给 C 部分用。
6. 给两个 MAC 各写一个只用来估时序的包装，放 `elinx/probe/`：所有输入、输出各打一拍。各估一次。这样输入到第一级寄存器、末级寄存器到输出的路径也算在里面。
7. 这五次都报：逻辑单元数、setup 最差裕量和这条路径的起点终点、hold 最差裕量。setup 裕量不到 4.0 ns 的，先改 RTL 再报。

   通用规则（每个测试、每个阶段都查）：

   | 编号 | 规则 |
   |---|---|
   | G1 | 抓包里每一帧的前导、帧长、FCS 正确；按第 3 节逐字段核对，各字段与当时的配置（`C`、`U` 行）和对应的消息（`M` 行）一致，包括 `port_en` 为 0 时用默认端口、n 小于 17 时补 0 |

   | G4 | SN：每条 VL 复位后第一帧为 0，之后 1 到 255 循环。IP 标识：按起始先后每次发送加 1，复位后从 0 开始，A、B 两份相同 |
   | G5 | 两网都启用的 VL：A、B 两份起始周期相同、长度相同，只有第 11 字节和 FCS 不同。只启用一网的 VL：另一网上没有它的帧 |
   | G6 | 同一条 VL 相邻两帧的起点间隔不小于 `bag` |
   | G7 | 起始时刻。记这一帧的起点为 S，它的消息最后一个字节被收下的周期为 A，它的到点时刻为 T，线上前一帧结束后的第一个周期为 E。`L = max(T, E + 96)`（没有的项不算）。要求 `L ≤ S ≤ max(L, A + 100)`。只有一种情况不查上限：S 之前的 2000 个周期里，别的 VL 有消息已被收下而帧还没起始，并且那条消息的到点时刻早于 S + 512 |

   G2 里有两处事先说不准：“队列满”取决于前一条消息出队了没有，“无空闲页”取决于页还回来没有。核对程序按上下界判：两种结果都可能时都算对，并把这样的条数记在 `either` 里。出队的时刻按“不早于线上前一帧的起点、不晚于本帧的起点”算；一页最早在读它的那一帧起始时还回、最晚在那一帧结束后 16 个周期还回。测试要设计得让 `either` 很少。

### 决定（由你写进 `ARCH.md`，见“文档”一节）

**J1 配置写怎样避开查表。** 不做旁路，只做“避开”。

- `afdx_tx_engine` 增加输出 `cfg_ok`，含义是“这一拍我不会发出 `tx_cfg` 的读”：`cfg_ok = enable && op==IDLE && !want_enq && !want_grant`。`afdx_rx_engine` 增加输出 `cfg_ok`，含义是“这一拍我不会发出 `rx_map`、`rx_cfg` 的读”：`cfg_ok = enable && (op==IDLE || op==AGE) && !desc_a_valid && !desc_b_valid`。
- 两个核心的外壳里，配置写的那一级寄存器只在 `cfg_ok` 为 1 时收下写：发送侧 `cfg_write <= cfg_we && cfg_ok`，接收侧 `map_we <= cfg_map_we && cfg_ok`、`cfg_we <= cfg_cfg_we && cfg_ok`。两个核心各增加一个输出端口 `cfg_ok`，放在端口表最后。从此核心的配置口是握手：写使能和 `cfg_ok` 同拍为 1 才算写进去。
- 道理：引擎的读使能寄存器和外壳的写使能寄存器在同一个时钟沿装入，下一拍才作用到 RAM。`cfg_ok` 为 1 的那一拍引擎不装读使能，所以下一拍 RAM 上只有写。
- `cfg_ok` 是组合信号，用到引擎自己的寄存器和兄弟模块直接来自寄存器的输出（入队请求、帧描述有效、`grant_ready`）。这是第 9 节第 9 条的一个例外，写进那一条。
- 等待上限仍是 64 个周期。Claude 的估算：发送侧最坏是 START、ENQ、GRANT 连着做，约 25 个周期；接收侧最坏是两网各来一帧，约 30 个周期。
- Claude 已经在自己的临时 worktree 里试过上面的改法（`worktrees\active\c3_claude_scratch`，那是 Claude 的，不要动，也不用看），外加两个骨架里各一条“配置写的那一拍 `cfg_ok` 为 1”的检查：17 项回归全过；`tb_tx_*`、`tb_rx_*` 共 13 次运行里的 10,333 次配置写，`cfg_ok` 都是 1；43 个事件记录和抓包文本与改之前逐字节相同。所以这条改动不许改变 T3、T4 任何一个测试的记录。

**J2 新模块 `afdx_cfg`。** 地址译码、寄存器、25 个计数器、读出、一个“待写”寄存器。总线时序（t 是周期号）：

- 写：`cfg_wr` 和 `cfg_ready` 在 t 拍同为 1 才接受；`cfg_ready` 为 0 时来的写不理，主机要重发。`cfg_ready` 直接来自寄存器。
  - 写三张表：t+1 拍起 `cfg_ready` 为 0，待写寄存器把写使能、地址、数据保持不变地送给核心；核心的 `cfg_ok` 为 1 的那一拍（记为 u，u ≥ t+1）算写进去，u+1 拍 `cfg_ready` 回到 1。不受阻时 u = t+1，`cfg_ready` 只低一拍。u − t 不超过 64。
  - 写寄存器、写没有映射的地址：当拍完成，`cfg_ready` 不变。写没有映射的地址没有任何效果。
  - `tx_ready` 为 0 期间 `cfg_ready` 为 0。
- 读：`cfg_rd` 在 t 拍为 1，则 t+2 拍 `cfg_rvalid` 为 1、`cfg_rdata` 有效；其余时候 `cfg_rvalid` 为 0。读不看 `cfg_ready`，复位结束后随时可读，可以每拍都读。表的地址和没有映射的地址读出 0。同一拍读、写同一个寄存器，读到旧值。读数据的多路选择分两拍（第 9 节第 6 条）。
- 计数器：32 位，计满回 0，只有复位清零。t 拍读到的值 = 对应的统计脉冲在 t−1 拍及以前出现的次数（自上次复位起）。

**J3 地址。** 取消“总使能”（每条 VL 自己有 `en`）。

| 地址 | 内容 |
|---|---|
| `0x00000` | VERSION，只读，`0xC3050000` |
| `0x00001` | STATUS，只读，位 0 是 `tx_ready`，其余为 0 |
| `0x00002` | USER_ID，可读写，位 15:0，复位值 0，接到发送核心的 `user_id` |
| `0x00040` 到 `0x00046` | 发送计数器，只读，依次是 accept、drop_dis、drop_full、drop_long、drop_nopage、tx_a、tx_b |
| `0x00048` 到 `0x0004F` | 接收 A 网计数器，只读，依次对应 `ev_a` 的位 0 到位 7 |
| `0x00050` 到 `0x00057` | 接收 B 网计数器，同上 |
| `0x00058`、`0x00059` | rm_drop、deliver |
| `0x00080` 到 `0x00FFF` | 留给 RTC 和服务，现在没有映射 |
| `0x01000 + vl×8 + w` | `tx_cfg`，只写 |
| `0x10000 + VLID` | `rx_map`，只写，数据取位 12:0 |
| `0x20000 + idx`（idx 小于 4096） | `rx_cfg`，只写 |

上表以外的地址都没有映射。译码：地址位 17:10 等于 `0000_0100` 是 `tx_cfg`；位 17:16 等于 `01` 是 `rx_map`；位 17:12 等于 `10_0000` 是 `rx_cfg`。

**J4 `AFDX_top` 的端口。** 第 2 节已有的端口不变，增加：

  - `*_tx`：抓包是这个端系统的两条发送线路（网络模型之前）；事件有 `G`、`P`、`Z`、`R`、`N`、`C`（表 `tx`）、`U`、`M`、`E`（发送侧的名称）。
  - `*_rx`：抓包是这个端系统的两条接收线路（网络模型之后）；事件有 `G`、`P`、`Z`、`R`、`I`、`K`、`C`（表 `map`、`cfg`）、`D`、`E`（接收侧的名称）。
  - `P` 行四个文件里都记。`N` 和 `K`：测试平台里给每个端系统放一个“影子” `afdx_timebase`，接同一个 `clk` 和 `reset`，从它读 `now`、`now_c`，不看顶层内部。每次复位结束各记一行。`K` 的步长是 4096。
  - `I`：`tx_ready` 变 1 的第一个周期。
  - `C` 的周期取 u（核心收下写的那一拍，等于 `cfg_ready` 回到 1 的那一拍减 1）。
  - `U`：每次复位结束记一行 0；写 USER_ID 时再记一行，周期取 t+1。
- `sys_events.txt`：总线上每一次读写（含读回的值、写等了几拍）、网络模型的每一个动作、阶段标记。格式你定，写进 `ARCH.md` 第 10 节。

**J7 时延和抖动的定义**（单位是周期，1 个周期 10 ns）。对每条交付了的消息：M 是它在发送端被收下的周期（`M` 行）；S 是载着它的帧在发送端线路上的起始周期；F 是被交付的那一份在接收端线路上结束的周期（起始周期 + 8 × 字节数）；D 是接收端 `D` 行的周期；P 是同一条 VL 上一帧的 S（没有上一帧就不算这一项）；BAG 是这条 VL 的 `bag`。

- 等待 W = S − max(P + BAG, M)，它就是这一帧的发送抖动。上限按 P7 的公式：4000 + 这个端系统所有已启用 VL 的 (20 + Lmax) × 8 之和，其中 Lmax = 47 + max(`max_payload`, 17)。
- 接收时延 = D − F，上限 15000（P7 的 150 µs）。
- 端到端 = D − M，只报告，不设统一上限（里面含 BAG 等待和链路延迟）。
- W 超出上限时不要改 RTL：把那一帧前后的情况写进摘要就行（提前选中的 VL 会让线路最多空等 512 个周期，理论上可以叠加，要不要处理由 Claude 定）。

### T5 补充裁定 1（2026-10-07）

Codex 开工后指出卡里三处自相矛盾，都成立。裁定如下，上文与这里不一致的以这里为准。这几条连同 J7 一起写进 `ARCH.md` 第 10 节新增的部分。

**R1 一条消息应当有几条 `D`。** 代替 S1 里的“一条 `M` 至多对应一条 `D`”和 `tb_sys_delay` 里的“`D` 行里的网应当是先到的那一网”。“恰好一次”是两网时间差不超过 `skew_max` 时的性质；超过时，后到的一份按新帧交付（`ARCH.md` 第 6.4 节第 5 步），系统测试要如实测到。

- 一条得到 `accept` 的消息在每一网上各有一份帧。同时满足下面三条的叫“有效份”：
  1. 发送端这条 VL 启用了这一网，这份帧没有被链路动作丢掉、改动或扣下（只加延迟的不算动过）；
  2. 接收端 `rx_map` 里有这个 VLID，`rx_cfg` 里 `en` 为 1、这一网启用、n 不大于 `max_payload`；
  3. n 不大于接收端环形缓冲的容量。
- 应有的 `D` 条数：

  | 情况 | 条数 |
  |---|---|
  | 没有有效份 | 0 |
  | 接收端 `rm_en` 为 1，普通阶段 | 1 |
  | 接收端 `rm_en` 为 1，“界外”阶段 | 每个有效份 1 条 |
  | 接收端 `rm_en` 为 0 | 每个有效份 1 条 |

  任何情况下，同一网的同一份至多交付一次；每条 `D` 都要对得上一条 `accept` 的 `M`（这一句不变）。
- “界外”阶段只在 `tb_sys_delay` 里有，阶段标记里写明。这种阶段里，同一条 VL 相邻两条消息的间隔要大于两网延迟差加 10000 个周期，保证上一条消息后到的那一份先于下一条消息先到的那一份到达。不这样安排会乱序交付，那是 P7 在界外本来就不保证的，不测。
- 复位阶段（`tb_sys_reset`）不查“应有几条”，只查“每条 `D` 对得上一条 `M`”和“同一份至多交付一次”。
- 来自哪一网，只在没有链路动作的阶段和 `tb_sys_delay` 里查。只有一条 `D` 时，它来自帧尾先到的那个有效份；两份的帧尾在同一拍算 A 网；相差 1 到 15 拍的不查（第 6.4 节不作规定），测试避开这样的延迟差。有两条 `D` 时，它们的先后与两份帧尾的先后一致。
- 有链路动作的阶段只查条数，不查来自哪一网（那由接收核对按参考模型查）。设计阶段时避免“某一网上同一条 VL 连续两帧到不了 rx_engine”（连丢两帧、连坏两帧、连着两条溢出）：否则下一帧过不了完整性检查，上面的条数规则就不成立了。
- S2 相应改为：把每条 `D` 对到它的 `M` 上，同一条 VL 的 `D` 依次对应的 `M` 的序号不减。
- 界线两侧的两对：一对的两份到达时刻正好差 `skew_max` 个单位（应有 1 条 `D`），一对正好差 `skew_max` + 1 个单位（应有 2 条）。消息的时刻要选得让这四份帧的到达时刻都没有两可：接收核对对这两对的判定必须是唯一的，不能落进 `either`。

**R2 `tb_sys_ovf`。** 由 R1 的第 3 条解决：n 大于环形缓冲容量的消息没有有效份，应有 0 条 `D`。这个测试另外要守三条：只用这一种“必然溢出”的消息造溢出，不靠缓冲里有积压；两条这样的消息之间至少隔一条正常交付的短消息；接收端两网的 `ovf` 计数器各自增加的数目等于这一网上这种帧的个数。

## 方向调整 1（2026-10-08，依据官方答疑 1008 版）

依据只有两份：赛题 PDF 和官方答疑表（`FPGA创新大赛问题汇总1008.xlsx`）。其余文档（包括本目录的 `ARCH.md`）只作参考，与这两份不一致时以这两份为准。

**答疑新增的结论（行号是答疑表的行）：**

- R61：模板里的 8 位收发口是 GMII，即 PHY 一侧的接口；MAC 可以用 eLinx 的 IP（不是必须）；“MII可能达不到规定的吞吐率”。
- R58：“传输速率 100 Mbps”指吞吐率达到 100 Mbps。
- R59：“时钟频率要与接口速率匹配。”
- R60：“GMII接口的延时不超过2ms即可。”
- R62：`rx_ready` 可以完全不用，`tx_ready` 取值不作要求，评测不检查 ready，`valid` 为 1 即表示该拍数据有效。
- R57：eLinx 的 MAC IP 用例化时生成的 `.vo` 文件仿真。

**与现状的差距：** C3 的线路是 100 MHz 下每 8 个周期一个字节，线速 100 Mbps，载荷吞吐最高 95.6 Mbps；既不是时钟匹配的 GMII，也到不了 100 Mbps 吞吐。

**裁定：**

1. 全设计仍是单时钟，频率改为 125 MHz（GMII 的时钟）。所有以周期计的常数不变，以时间计的量按 8 ns 一个周期重算。
2. 收发核心不改，内部仍是每 8 个周期一个字节（等效 125 Mbps，载荷吞吐最高约 119.6 Mbps）。
3. `AFDX_top` 的每个网口加 GMII 速率适配：发送侧把核心送出的帧存下，每一帧都在核心起始时刻之后同一个固定延迟处开始，以每周期一个字节连续送出；接收侧把线上的连续帧存下，再按核心的节拍送给核心，放不下的整帧丢弃并计数。
4. MAC 用自己的，不用 eLinx 的 IP。
5. 吞吐率、时延、抖动都在 GMII 口上测量并写进测试报告。

**不做的方案：** 把收发核心改成每周期一个字节的原生千兆（吞吐可到约 950 Mbps）。它要重开 T2 到 T4：`afdx_tx_builder` 取载荷要 3 拍、页归还的握手、接收侧“引擎在下一帧第 42 字节前给出结论”的规则，都依赖每字节 8 拍的余量。赛题只要求 100 Mbps，余下的三项功能更要紧；留作以后可选的升级。

## T6：125 MHz、GMII 速率适配、在 GMII 口上验证和测量、顶层综合后仿真

**目的。** 落实“方向调整 1”：模板的 8 位收发口变成真正的 GMII（125 MHz，每周期一个字节，帧内 `valid` 连续），吞吐率达到 100 Mbps 以上，并在 GMII 口上量出吞吐率、时延、抖动；整个顶层通过综合后网表仿真。

**依据。** 官方答疑 R58、R59、R60、R61、R62、R46（见“方向调整 1”和“时序的验收口径”），`ARCH.md` v0.5，和下面的“决定”。不一致时以本卡为准；遇到卡里自相矛盾按 T5 的 R5 处理。

**不许动的。** `afdx_tx_core`、`afdx_rx_core` 以及它们下面的全部模块、`afdx_timebase`、`afdx_ram_sdp` 一个字不改。核心级的 17 项测试和 43 份记录保持逐字节不变。认为必须改时停下来报告。

### 决定

**L1 时钟。** 单时钟 125 MHz，周期 8 ns。RTL 里以周期计的常数都不变。测试平台的时钟周期、抓包转 pcap 的时间戳、所有“周期换算成时间”的地方改成 8 ns。配置里以时间定的量按 8 ns 重算：1 ms 是 125000 个周期；`now_c` 的一个单位是 4096 个周期，即 32.768 µs；P7 抖动公式里的 40 µs 是 5000 个周期，500 µs 是 62500 个周期。公式里的带宽取核心的线速 125 Mbps（一个周期一位），所以“所有已启用 VL 的 (20 + Lmax) × 8 之和”这一项以周期计不变。J7 的 W 上限相应改成 5000 + 这一项。

**L2 发送适配 `afdx_gmii_tx`（每网一个）。** 输入是核心的慢线（每字节 8 个周期，`valid` 整帧为 1），输出是 GMII。

- 慢线上的帧按字节存入缓冲。记一帧在慢线上的起始周期为 S（`valid` 由 0 变 1 的那个周期），它在 GMII 上的起始周期恰好是 S + D，然后每周期一个字节连续送完，帧内 `tx_valid` 不许出现 0，字节内容和个数与慢线上的完全相同（从第一个前导字节到 FCS 最后一个字节）。
- D 对所有帧是同一个常数，与帧长、与前面有没有帧都无关。取值规则：保证慢线上最长的帧（1526 个字节，含前导）不读空的最小值，再向上取整到 64 的倍数。Claude 的估算是 10688（7 × 1525 = 10675，加上取数的几拍）。做成 `localparam`，实际取值和推导写进 `ARCH.md`。
- 这样 GMII 上相邻两帧起始的间隔与慢线上的逐周期相等，核心做出来的 BAG 和抖动原样保留；GMII 上的帧间空闲不会少于 96 个周期。
- 缓冲深度按最坏情况定并留余量（D 个周期内慢线最多写入约 1340 个字节、最多约 16 帧）。不许溢出：加一条只在仿真时存在的检查，溢出或读空就打印 `** Error: [GMIITX]`。
- 复位期间输出为 0。复位后的行为与核心一致，不需要额外等待。

**L3 接收适配 `afdx_gmii_rx`（每网一个）。** 输入是 GMII，输出是给核心的慢线。

- `rx_valid` 由 0 变 1 是一帧的开始，变回 0 是结束；帧与帧之间只要有 1 个周期的 0 就算两帧。适配器不看帧的内容，好坏仍由核心判。
- 帧按字节存入缓冲，再按每字节 8 个周期重放给核心，重放的帧内 `valid` 连续为 1，字节内容和个数与 GMII 上的完全相同。
- 缓冲里没有别的帧时：重放的起始周期 = GMII 起始周期 + 常数 R（你定，不超过 16），对所有这样的帧相同。这样两网之间的到达时间差原样传给核心。
- 缓冲里还有前一帧没重放完时：前一帧重放结束后隔正好 16 个周期开始重放这一帧（核心在 T4 里测过 8 个周期的间隔）。
- 放不下的帧整帧丢弃：一帧开始到达时或到达途中缓冲不够，这一帧已经写入的部分作废，不重放任何一个字节，给一个单周期脉冲并计数；后面的帧照常收。已经开始重放的帧不会被丢弃，所以判断“放不放得下”的做法要保证这一点（例如写满时如果这一帧已开始重放，说明它是队首，读指针在前进，不会满；具体做法你定并写进 `ARCH.md`）。
- 缓冲深度是参数 `GMII_RX_AW`，默认 12（4096 个字节）；另有帧队列。对端也是本设计时（慢线节拍、帧间 96 个周期），任何流量下都不许丢帧。
- `tx_ready` 为 0 期间到达的帧整帧不理，也不计数。复位期间输出为 0。

**L4 `AFDX_top`。** 两种适配器各两个，放在核心和引脚之间。模板端口名不变：`tx_data`、`tx_valid` 是 A 网的 GMII 发送，`rx_data`、`rx_valid` 是 A 网的 GMII 接收；`*_b` 是 B 网。`tx_ready`、`rx_ready` 照旧。新增输出端口 `ev_gdrop[1:0]`（位 0 是 A 网接收适配的丢弃脉冲，位 1 是 B 网）。参数增加 `GMII_RX_AW`。`afdx_cfg` 增加两个只读计数器：`0x0005A` 是 A 网的 gdrop，`0x0005B` 是 B 网的，规则同原有的 25 个。VERSION 改为 `0xC3060000`。顶层端口总位数报出来，不许超过 339。

**L5 记录。** 一次系统测试的输出目录里：

- 原有四个子目录 `es1_tx`、`es1_rx`、`es2_tx`、`es2_rx` 的格式和含义不变，记的仍是**核心边界上的慢线**（现在是顶层内部的信号，测试平台用层次路径去看；这是唯一允许看内部信号的地方）。原有的收发核对和 Claude 的两个核对程序照旧读它们。
- 新增 GMII 口的抓包：每个端系统的两条 GMII 发送线路、两条 GMII 接收线路，格式同第 10 节第 6 条（起始周期、字节数、十六进制串），每字节 1 个周期。目录和文件名你定。
- 网表仿真看不到内部信号：`tb_sys_net` 跑网表时只记 GMII 抓包、`D` 行和 `sys_events.txt`，要求它们与 RTL 那一次逐字节相同。

**L6 链路模型改到 GMII。** 两个 `AFDX_top` 的 GMII 口经链路模型对接，丢、改、扣下重放、插入、延迟都按 GMII 帧做（每周期一个字节）。重放和插入的帧与前后的帧在 GMII 上至少隔 12 个周期。原有八个系统测试的场景全部保留，改到 GMII 上；`skew_max`、延迟差这些和时间有关的参数按需要重新选，保证 R1 的各条仍然成立（界线两侧的两对仍要判定唯一）。

**L7 GMII 层的核对（新写，放 `tools/`，进 `eda.py`，每个系统测试多一行 `[CHECK]`）。**

- X1 每条 GMII 发送线路的帧与同一网慢线发送抓包的帧一一对应、逐字节相同，起始周期恰好差 D。
- X2 GMII 发送线路上帧内 `valid` 连续（由监视器当场查），帧间空闲不少于 12 个周期。
- X3 链路如实（原 S3 改到 GMII 上）：每条 GMII 接收线路的抓包 = 对端 GMII 发送抓包按链路动作变换的结果。
- X4 每条慢线接收抓包（重放）的帧 = 同一网 GMII 接收抓包里没被适配器丢弃的帧，顺序相同、逐字节相同；重放起始周期符合 L3 的两条规则；丢弃的帧数 = gdrop 脉冲数 = 计数器读值。
- X5 原 S1、S2、S4、S5、S6 照旧（S6 用 L1 的新上限）。
- 自检：给 X1 到 X4 各造一种篡改过的记录，都要报错。

**L8 指标测量（新测试 `tb_sys_perf`，RTL 上跑，进回归）。** 都在 GMII 口上量，数字进摘要，以后原样进测试报告。

- 吞吐率：ES1 到 ES2 方向 9 条 VL，BAG 1 ms（125000 个周期），每条消息 1471 个字节，每条 VL 每个 BAG 送一条，各条 VL 的提交时刻错开；稳定后连续量不少于 20 ms。报三个数：GMII 上帧字节（不含前导，含 FCS）的速率、UDP 载荷的速率、接收端交付的载荷速率。要求：后两个都不低于 100 Mbps；这段时间里收下的消息全部交付恰好一次，没有任何丢弃计数增加。再加一个阶段：反方向同时也跑同样的流量（双向满载），同样的要求。如果 9 条跑不稳（收下被拒或出现丢弃），把现象报上来，不要改核心。
- 时延，三个量各报最大值和平均值，分“轻载”（一条 VL、消息间隔大于 BAG、线路空闲）和上面的“吞吐”两个阶段：
  - T_tx = 消息最后一个字节被收下的周期 → 载着它的帧在 GMII 发送口上第一个字节的周期；
  - T_rx = 帧在 GMII 接收口上最后一个字节的周期 → 交付的最后一个字节的周期；
  - T_e2e = 消息最后一个字节被收下 → 对端交付最后一个字节（链路延迟取 0 和一个固定值各一次，报的时候减去链路延迟）。
  - 要求（R60，2 ms = 250000 个周期）：轻载阶段三个量的最大值都不超过 250000；吞吐阶段 T_rx 不超过 250000，T_tx 和 T_e2e 减去该帧的 BAG 等待后不超过 250000。超出时照实报告，不改核心。
- 抖动：轻载和吞吐两个阶段，同一条 VL 相邻两帧在 GMII 发送口上的起始间隔与 BAG 之差的最大值，和 L1 的公式上限一起报。
- 规模：128 条发送 VL、4096 条接收 VL 的配置（已在 `tb_sys_load` 里）在 GMII 上照样通过，摘要里点明。

### T6 补充裁定 1（2026-10-08）

Codex 做完第 0 步（17 项通过，43 份记录不变）后指出 L3 自相矛盾：输入帧长没有上限、缓冲有限、帧一到就重放、放不下又要整帧一个字节不出，四条不能同时成立。成立，停下来问是对的。裁定如下，L3、L7 与这里不一致的以这里为准。

**M1 接收适配改为“收完整帧再重放”。**

- 一帧在 GMII 上完整结束、并且全程没有写满，才允许重放。没收完的、途中写满的帧不向核心输出任何字节；写满的整帧作废、给 gdrop 脉冲并计数，帧的剩余部分收到 `rx_valid` 回 0 为止都丢掉，下一帧照常收。比缓冲容量还长的帧必然被丢弃（这类帧不再到核心，核心的 `len` 计数只对放得下的超长帧有效，例如 1527 个字节的）。
- 重放起始周期 = max(GMII 帧结束周期 + R，上一帧重放结束周期 + 16)。R 是常数（你定，不超过 16），“帧结束周期”取 `rx_valid` 回 0 的那个周期。
- 不加输入帧长上限，`ARCH.md` 第 6.2 节的接收契约不变。
- Claude 的推算，供你核对并写进 `ARCH.md`：对端是本设计时，记排队造成的额外等待为 d，则 d(k+1) = max(0, d(k) + L(k) − L(k+1) − 80)，所以 d 不超过最长帧与最短帧的字节数之差（约 1454 个周期），缓冲占用有界，4096 个字节够用，不会丢帧。实测的最大 d 和最大占用报进摘要。
- 两网的到达时间差：同一条消息在两网上的帧一样长，两网都不排队时差值原样传给核心；有排队时最多偏 d。`tb_sys_delay` 界线两侧的两对要安排在两网都不排队的时刻。
- X4 的“重放起始周期符合 L3 的两条规则”改为符合上面这一条。

**M2 `tb_sys_perf` 用双网。** 两网都启用才是正常的 AFDX 配置。“没有任何丢弃计数增加”指的是：发送侧四种 drop、两网各自的 fcs、len、hdr、unk、cfg、ic、ovf、两个 gdrop 都不增加。`rm_drop` 是冗余管理丢掉后到的那一份，属于正常，要求它增加的数目等于这段时间交付的消息数。摘要里把这一点写明。

## T9b：615A 两处改正，RTC 报文改成标准 SNTP

**依据。** 615A 的两处是 T9 验收时对照规范查出来的。RTC 这一处：答疑 R48 对 SNMP、615A、RTC 的回答都是“建议参考协议规范”，SNMP 和 615A 已经用标准报文，RTC 现在是自定的 32 字节报文却用着 NTP 的端口 123，标准工具解不出来，是 Claude 定 T7 卡时的疏漏。执行规则第 12、13 条适用。限时 120 分钟，一次提交（`c3 T9b:`）。本卡可以改 `afdx_rtc` 和 `afdx_615a`；收发核心、GMII 适配器、`afdx_snmp` 不改。

**做什么。**

1. **615A 端口。** TFTP 请求的目的端口改为 59，做成配置寄存器，复位值 59。
2. **615A 超时和重试。** 超时做成配置寄存器（单位你定），复位值等于规范的 2 秒；重试次数按附件 4 的规定（请你读附件 4 第 3 节，取规范给的值做复位值，也做成可配置）。测试里把超时配成短的值来跑，不用真等 2 秒；摘要里写明规范值和测试用的值。
3. **RTC 报文改成标准 SNTP**（RFC 4330，也就是 NTP 的 48 字节报文）。
   - 从端发 mode 3（client），主端回 mode 4（server），版本号 4；Originate、Receive、Transmit 三个时间戳按标准放，主端把请求的 Transmit 原样抄进回应的 Originate。stratum 等其余字段填合理的固定值。
   - 时间戳是标准格式：32 位秒加 32 位二进制小数。内部时钟仍是秒加纳秒，纳秒和二进制小数之间的换算你定做法（多拍完成即可，不要求单拍）。秒的起点（NTP 从 1900 年算起）怎么对应你定，写进文档。
   - 对时算法、采样时刻、寄存器地址不变。
4. **测试。**
   - 原有的 RTC 测试改成新报文后全过；空载下从端与主端的误差不超过 40 ns。
